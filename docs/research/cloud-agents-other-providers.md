# Hosted cloud coding agents other than Claude Code: Codex, Cursor, Copilot and more

Facts for [Research: other hosted cloud coding agents - Codex, Cursor, Copilot and more (#70)](https://github.com/yahyabedirhan/skills/issues/70), under [Spec: research cloud agents (#45)](https://github.com/yahyabedirhan/skills/issues/45). Claude Code's own cloud options are on the sibling page [cloud-agents-claude-code.md](cloud-agents-claude-code.md) (#69). How the harnesses behave locally (instruction files, permissions, hooks, memory) is on [harness-capabilities.md](harness-capabilities.md) and isn't repeated here.

Researched 2026-09-29, and followed up the same day to settle the first pass's open questions from primary sources (see the [Exploration log](#exploration-log)). Every source below was read on that date. Nothing was signed up for, paid for, installed or run in any provider's cloud.

Evidence tags:

- **[doc]** the provider's official documentation, linked in each section's source list.
- **[src]** the provider's official public source, read through the GitHub API.
- **[blog]** the provider's official blog or changelog.
- **Unverified** marks a claim no primary source settles; each one is listed again under [Open questions](#open-questions) with why it stays open and the check that would settle it.

Two names changed recently, and the docs use the new ones: GitHub's "Copilot coding agent" is now **Copilot cloud agent**, and Cursor's "Background Agents" are now **Cloud Agents** ("Cloud agents were formerly called Background Agents") [doc cursor cloud-agent]. Codex calls its tasks **cloud chats** [doc codex cloud].

Findings that matter most for this effort:

- **Of the big three, only Cursor syncs user-level skills to the cloud,** and only from `~/.cursor/skills`; account User Rules also apply there [doc cursor skills; doc cursor best-practices]. For Codex and Copilot the documented personal skill folders are on the local machine [doc codex build-skills; doc copilot about-agent-skills]; every one of them reads the repo's `AGENTS.md`. Among the smaller ones, Amp hosts personal skills and a global `AGENTS.md` itself, and Devin picks up `SKILL.md` files from every repository connected to the organization, so a dedicated skills repository can serve them (§6).
- **All three of the big ones can be started, watched and pulled back by a local agent from a shell with documented commands:** Codex (`codex cloud exec`, `list --json`, `status`, `diff`, `apply`) [src codex cli.rs], Copilot (`gh agent-task create/list/view --log --follow`) [doc copilot cli], and Cursor through its REST API, which is the only one of the three where a local agent can send follow-ups to a running cloud agent [doc cursor api]. Codex has no follow-up command in its open-source client, and Copilot's steering exists only in the web prompt box (not in `gh agent-task`, the REST API or the GitHub MCP server) [src codex; src cli/cli; doc copilot REST reference; src github-mcp-server]. Devin (API `…/messages`, MCP) and Jules (API `:sendMessage`) also take follow-ups from a shell (§6).
- **Copilot has a hard 59-minute cap per session** [doc copilot about]. Codex publishes no limit at all; Cursor publishes no cap, and its long-running agents run for hours or days on Ultra, Teams and Enterprise [blog cursor long-running]; Amp orbs have only idle timeouts [doc amp sizes].
- **Two let the cloud agent's tool calls run on a machine the user owns,** which bears on the VPS question (#71, #72): Cursor's My Machines (`agent worker start` on a laptop, devbox or remote VM, agent loop in Cursor's cloud) [doc cursor my-machines], and Copilot on self-hosted Actions runners [doc copilot environment]. Factory's BYOM and Devin Outposts are the same idea (§6).

## 1. OpenAI Codex cloud

Sources [doc]: [Codex cloud](https://learn.chatgpt.com/docs/cloud) ("codex cloud"), [Cloud environments](https://learn.chatgpt.com/docs/environments/cloud-environment) ("codex env"), [Agent internet access](https://learn.chatgpt.com/docs/cloud/internet-access) ("codex internet"), [GitHub](https://learn.chatgpt.com/docs/third-party/github) ("codex github"), [Slack](https://learn.chatgpt.com/docs/third-party/slack), [Linear](https://learn.chatgpt.com/docs/third-party/linear), [CLI reference](https://learn.chatgpt.com/docs/cli/reference) ("codex cli"), [Build skills](https://learn.chatgpt.com/docs/build-skills), [Pricing](https://learn.chatgpt.com/docs/pricing), [Codex Remote](https://learn.chatgpt.com/docs/remote), [Scheduled tasks](https://learn.chatgpt.com/docs/automations). (`developers.openai.com/codex/...` redirects to these; each has a Markdown version at `<url>.md`, which is what was read.) Follow-up [doc]: [Custom instructions with AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md) ("agents-md"), [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents), [Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security), and the full export [`llms-full.txt`](https://learn.chatgpt.com/llms-full.txt), searched for cloud limits, browsers and branches. [src]: `openai/codex` `codex-rs/cloud-tasks/src/cli.rs` at commit `cf12c86` ("codex cli.rs", unchanged at `d5e6526`); at `d5e6526`, `codex-rs/ext/skills/src/host_roots.rs` ("codex host_roots.rs") and `codex-rs/backend-client/src/client.rs` plus `codex-rs/cloud-tasks-client/src/api.rs` ("codex backend-client"); `openai/codex-universal` README and Dockerfile (`47f4f0e`).

- **Environment.** Each chat gets a container that checks out the repo at the chosen branch or commit, runs the setup script (plus an optional maintenance script when a cached container is resumed), applies the internet settings, then runs the agent's terminal loop and shows a diff [doc codex env, "How Codex cloud chats run"]. The default image is `universal`, "pre-installed with common languages, packages, and tools"; `openai/codex-universal` is a reference image, built `FROM ubuntu:24.04`, with Python, Node, Rust, Go, Swift, Ruby, PHP and Java versions chosen by `CODEX_ENV_*` variables, plus bun, bazel, erlang and elixir; only linux/amd64 runs in Codex [doc codex env; src codex-universal]. Container state is cached for up to 12 hours; the cache is invalidated when the setup script, maintenance script, variables or secrets change [doc codex env, "Container caching"]. CPU, memory and disk aren't published; Business plans get "Larger virtual machines to run cloud chats faster" [doc pricing]. **Unverified:** default resources and any per-task time limit. The follow-up searched the full single-file docs export (`llms-full.txt`) and found no size, timeout or maximum run time for cloud chats; the 2025 launch post, which is said to give typical durations, refuses automated fetches (HTTP 403).
- **Tools.** Anything the setup script installs (it runs in its own Bash session with internet on, so `export` doesn't carry over; use `~/.bashrc` or environment settings). Automatic setup for npm, yarn, pnpm, pip, pipenv and poetry. Environment variables last the whole chat; **secrets reach only the setup script** and are removed before the agent phase [doc codex env].
- **Web and browser.** Agent-phase internet is **off by default**; per environment it can be turned on with a domain allowlist (None, a "Common dependencies" preset that includes `github.com`, or All) and limited to `GET`, `HEAD`, `OPTIONS`. All traffic goes through an HTTP/HTTPS proxy [doc codex internet; doc codex env]. No browser is documented, and the reference Dockerfile installs none [src codex-universal]. The follow-up found browser and Computer Use tools in the docs only for the local app and ChatGPT Work, never tied to Codex cloud chats. **Unverified:** whether a setup script can install and use a headless browser; nothing in the docs forbids or describes it.
- **What loads.** The repo's `AGENTS.md`: "If your repo includes `AGENTS.md`, the agent uses it to find project-specific lint and test commands" [doc codex env]; for review, `## Code Review Rules` sections in the nearest `AGENTS.md` [doc codex github]. Skills are read from `.agents/skills` from the working directory up to the repo root, from `$HOME/.agents/skills`, and from `/etc/codex/skills` [doc build-skills]. The open-source loader matches: `codex-rs/ext/skills/src/host_roots.rs` adds `$CODEX_HOME/skills` (deprecated) and `$HOME/.agents/skills` as user roots, the system config folder's `skills` as the admin root, and `.agents/skills` in every folder from the project root down to the working directory [src codex host_roots.rs]. Global instructions come from `$CODEX_HOME/AGENTS.md` (default `~/.codex`) [doc agents-md]. So a setup script that writes into `$HOME/.agents/skills` or `~/.codex/AGENTS.md` would be picked up **if** the cloud agent runs this loader in the container's home folder. **Unverified:** that "if". The cloud harness isn't in the open-source repository (the CLI's cloud client only creates, lists, diffs and applies tasks through the ChatGPT backend [src codex backend-client]), and no doc says which skill roots a cloud chat reads. The local global `~/.codex/AGENTS.md` isn't in the container (it lives on the local machine).
- **GitHub.** Connect GitHub (or GitLab, beta) when prompted and choose the repositories Codex can access [doc codex cloud, "Getting started"]. After a chat, "open a pull request when the work is ready" from the web [doc codex cloud]. On a pull request, `@codex review` posts a review, and `@codex <anything else>` "starts a cloud chat using your pull request as context" that "can push a fix back to the branch when it has permission to do so" [doc codex github]. A chat starts from "the selected branch or commit SHA" [doc codex env], and `codex cloud exec --branch` picks it [src codex cli.rs]. **Unverified:** the branch name a web-opened PR uses and its base, and whether a chat can push to an arbitrary existing branch. PR creation happens in the ChatGPT backend, which isn't open source, and no doc page names the branch.
- **Starting it.** Web (`chatgpt.com/codex`), the desktop app's Cloud option, the IDE extension, the CLI, GitHub `@codex`, Slack `@Codex`, Linear (assign or mention) [doc codex cloud; doc slack; doc linear]. **From the CLI:** `codex cloud exec --env ENV_ID [--attempts 1-4] [--branch BRANCH] "QUERY"`; `--env` is required, and `--branch` "defaults to current branch" [doc codex cli; src codex cli.rs]. The environment must first be created in the web settings. `codex cloud` is marked experimental [doc codex cli].
- **Long work.** Best-of-N attempts (1–4) per task [doc codex cli]. **Unverified:** sub-agents inside a cloud chat (the subagents page covers the desktop app, CLI, IDE and ChatGPT Work, not Codex cloud [doc subagents]), and a maximum run time.
- **Watching and answering.** Watch logs on the web or "let the task run in the background" [doc codex cloud]. From a shell: `codex cloud list [--env] [--limit 1-20] [--json]` gives each task's `id`, `url`, `title`, `status`, `updated_at`, `summary`, `attempt_total` [doc codex cli]; the source also has `codex cloud status TASK_ID` and `codex cloud diff TASK_ID [--attempt N]`, which the docs page doesn't list [src codex cli.rs]. There is **no CLI command to send a follow-up** to a running chat [src codex cli.rs]; follow-ups are on the web, or by a new `@codex` comment on the pull request. Slack and Linear post results back to the thread or issue [doc slack; doc linear]. **Unverified:** push notifications.
- **Moving it.** `codex apply TASK_ID` (alias `codex a`) or `codex cloud apply TASK_ID [--attempt N]` applies the task's latest diff to the local working tree and exits non-zero on conflicts [doc codex cli; src codex cli.rs]. Or open the PR and check out its branch. There's no documented way to move a local session into the cloud with its conversation.
- **Cost and limits.** Cloud chats are included in Plus ($20/month), Pro (from $100), Business and Enterprise/Edu, not with an API key ("No cloud-based features") [doc pricing]. "Local messages and cloud chats share your plan's usage allowance", and "Cloud chats on ChatGPT plans use GPT-5.6 Sol and may use more of your allowance than local messages"; five-hour and weekly limits apply [doc pricing].
- **Not a cloud agent:** Codex Remote drives tasks on the user's own connected computer from a phone [doc remote], and scheduled tasks in the desktop app need the computer on [doc automations].

## 2. Cursor Cloud Agents (and the `agent` CLI)

Sources [doc], each read as Markdown at `<url>.md`: [Cloud Agents](https://cursor.com/docs/cloud-agent) ("cursor cloud-agent"), [Setup](https://cursor.com/docs/cloud-agent/setup) ("cursor setup"), [Capabilities](https://cursor.com/docs/cloud-agent/capabilities) ("cursor capabilities"), [Security and network](https://cursor.com/docs/cloud-agent/security-network) ("cursor network"), [Cloud Agents API](https://cursor.com/docs/cloud-agent/api/endpoints) ("cursor api"), [My Machines](https://cursor.com/docs/cloud-agent/self-hosted/my-machines) ("cursor my-machines"), [Skills](https://cursor.com/docs/skills) ("cursor skills"), [Subagents](https://cursor.com/docs/subagents), [CLI usage](https://cursor.com/docs/cli/using), [CLI parameters](https://cursor.com/docs/cli/reference/parameters), [GitHub](https://cursor.com/docs/integrations/github), [Slack](https://cursor.com/docs/integrations/slack), [iOS](https://cursor.com/docs/cloud-agent/mobile), [Models and pricing](https://cursor.com/docs/models-and-pricing). Follow-up: [Best practices](https://cursor.com/docs/cloud-agent/best-practices) ("cursor best-practices"), [Settings](https://cursor.com/docs/cloud-agent/settings) ("cursor settings"), [Rules](https://cursor.com/docs/rules), [Rules help](https://cursor.com/help/customization/rules) ("cursor rules help"), [Webhooks](https://cursor.com/docs/cloud-agent/api/webhooks); [blog] [Expanding our long-running agents research preview](https://cursor.com/blog/long-running-agents) (2026-02-12, "cursor long-running").

- **Environment.** "Cloud agents run on isolated Ubuntu machines", each an isolated VM "with a full desktop environment" [doc cursor setup; doc cursor capabilities]. Configure by agent-led setup, a saved snapshot, or a Dockerfile named in `.cursor/environment.json` (resolved first from the repo file, then a personal, then a team environment); Builds run the `install` script ahead of time and capture disk state, then `start` and `terminals` (in a `tmux` session shared by you and the agent) run at boot [doc cursor setup]. "Each cloud agent runs on a default VM profile with limited memory and CPU"; Enterprise can ask for more [doc cursor setup, "Resource limits"]. Snapshots are kept up to 90 days after last use; conversations indefinitely [doc cursor network, "Data retention"]. Multi-repo environments are supported [doc cursor setup]. **Run time:** no cap is published. Team admins have a **Long running agents** toggle that "controls whether team members can run agents for extended durations" (not yet for multi-repo environments) [doc cursor settings]; the research preview opened long-running agents to "all Ultra, Teams, and Enterprise users" and cites runs of 25, 30 and 36 hours [blog cursor long-running]. **Unverified:** exact CPU, memory and disk (only "limited memory and CPU"; "Self-serve custom resource configuration is coming soon" [doc cursor setup]), and whether ordinary cloud agents on Pro stop after some time.
- **Tools.** Whatever the Dockerfile or install script adds; Docker, Tailscale and Cloudflare Tunnel are documented; secrets from the dashboard arrive as environment variables when the agent starts [doc cursor setup; doc cursor cloud-agent]. MCP servers over HTTP (proxied, credentials never on the VM) or stdio (run on the VM), plus a built-in Cursor Cloud MCP for run diagnostics [doc cursor capabilities].
- **Web and browser.** "The agent has internet access by default"; users, teams and environments can restrict it to "Default + allowlist" or "Allowlist only" [doc cursor network]. **It can drive a browser and desktop** ("computer use"), record screenshots and videos as artifacts, and the user can take over its remote desktop [doc cursor capabilities]. The agent "auto-runs all terminal commands" [doc cursor network].
- **What loads.** "Cloud agents read `AGENTS.md` files" [doc cursor setup]. Repo `.cursor/hooks.json` hooks run (team and enterprise hooks on Enterprise); **user hooks in `~/.cursor/hooks.json` don't**, "since cloud VMs don't have access to your local home directory" [doc cursor cloud-agent, "Hooks support"]. **User skills:** "Only `~/.cursor/skills/` syncs" to Cloud Agents, after turning on **Sync Skills for Cloud Agents**; `~/.agents/skills/` and project skills "stay local" in that sync, and project skills come with the clone [doc cursor skills, "Use personal skills with Cloud Agents"]. Cursor also loads `.claude/skills/`, `.codex/skills/` and their home equivalents locally [doc cursor skills]. MCP servers come from the team's configuration at `cursor.com/agents`, not the local session [doc subagents]. **User Rules do apply:** "Cloud Agents can read and follow Rules at three levels": user rules "Set in Cursor Settings, these apply to your sessions across all repositories", team rules, and repo rules [doc cursor best-practices]. Account user rules "are stored on your Cursor account" and sync, while user rule *files* in `~/.cursor/rules` "stay on the machine and do not sync" [doc cursor rules help], so only the account ones reach the cloud. (Whether the `agent` CLI applies account User Rules locally is a separate question, still open in [harness-capabilities.md](harness-capabilities.md) §4.1.)
- **GitHub.** A Cursor admin connects the Cursor GitHub app (also GitLab, Bitbucket, Azure DevOps); you need read-write access to the repo [doc cursor cloud-agent; doc cursor github]. The agent works "on a separate branch, then push[es] changes to your repo" [doc cursor cloud-agent]. Through the API, `workOnCurrentBranch: false` (default) pushes to a new `cursor/...` branch, `true` pushes straight to `startingRef` or the PR's head branch; `autoCreatePR` opens a pull request; `prUrl` works on an existing PR [doc cursor api, "Create An Agent"]. It auto-fixes failed GitHub Actions checks on PRs it opened (Teams only for now) [doc cursor capabilities].
- **Starting it.** iOS app, web (`cursor.com/agents`), the desktop app's Cloud option, Slack `@cursor`, GitHub or Bitbucket `@cursor` comments, Linear, and the API [doc cursor cloud-agent]. In the `agent` CLI, prefixing a message with `&` pushes the conversation to a Cloud Agent [doc cli using, "Cloud Agent handoff"]; in the desktop app, `/in-cloud` starts a cloud subagent [doc subagents]. **For a local agent, the API is the non-interactive path:** `POST https://api.cursor.com/v1/agents` with a user API key, `prompt.text`, `repos[].url`, `startingRef`, `autoCreatePR`, optional `envVars`, `mcpServers` and `model` [doc cursor api]. The API is a public beta [doc cursor api].
- **Long work.** Subagents work in Cloud Agents, each with its own branch and possibly its own VM [doc subagents]. **Subscriptions** let an agent end its turn and wake on GitHub PR activity or CI results, Slack replies, Linear changes, or a timer, for up to 180 days [doc cursor capabilities, "Subscriptions"]. Automations run cloud agents "on a schedule or in response to events from GitHub, GitLab, Slack, webhooks, Linear, and more" [doc [Automations](https://cursor.com/docs/cloud-agent/automations)].
- **Watching and answering.** Web, desktop and iOS (push notification when a turn ends), Slack completion messages with the PR link [doc cursor ios; doc cursor slack]. From a shell, the API gives `GET /v1/agents/{id}`, `GET …/runs/{runId}`, an SSE stream `GET …/runs/{runId}/stream` (events `status`, `assistant`, `tool_call`, `result` with the pushed branches, `done`), and **follow-ups** with `POST /v1/agents/{id}/runs` (one active run at a time; `409 agent_busy` otherwise) [doc cursor api]. Webhooks exist only in the legacy v0 API, sending `statusChange` events for `ERROR` or `FINISHED`; for the current API they are "coming soon" [doc cursor api; doc webhooks].
- **Moving it.** Local to cloud: `&` in the CLI, `/in-cloud` in the app [doc cli using; doc subagents]. Cloud to local: check out the pushed branch; artifacts and the remote desktop let you test without it [doc cursor capabilities]. **Unverified:** a documented "continue this cloud agent locally" command.
- **Running on your own machine.** My Machines: `agent worker start` on "a laptop, devbox, or remote VM" opens an outbound connection; "the agent loop runs in Cursor's cloud, but terminal commands, file edits, browser actions, and other tool calls execute on your machine"; the machine then appears in the environment picker [doc cursor my-machines]. API `env.type: "machine"` or `"pool"` targets it [doc cursor api]. This would let a Cursor Cloud Agent use the VPS's own tools and state; see #71.
- **Cost and limits.** Cloud Agents come with Pro ($20/month), Pro Plus ($60), Ultra ($200) and Teams; they are "charged at API pricing for the selected model", and you set a spend limit on first use [doc models-and-pricing, "Plans"; doc cursor cloud-agent, "Billing"]. A paid plan is required [doc cursor cloud-agent, "Troubleshooting"].

- **Environment.** "Its own ephemeral development environment, powered by GitHub Actions" [doc copilot about]. Default Ubuntu Linux; Windows 64-bit also supported; macOS isn't [doc copilot environment]. A standard `ubuntu-latest` runner has 4 CPU, 16 GB RAM, 14 GB SSD on public repositories and 2 CPU, 8 GB on private ones [doc hosted runners]; larger and self-hosted runners are allowed (self-hosted needs the integrated firewall turned off) [doc copilot environment]. **Each session is capped at 59 minutes**, "a hard limit that cannot be extended" [doc copilot about].
- **Tools.** `.github/workflows/copilot-setup-steps.yml` (one job named `copilot-setup-steps`) preinstalls tools, picks the runner, sets `timeout-minutes` (max 59) and Git LFS; if a step fails, the agent starts anyway with what it has. The file only takes effect once it's on the default branch [doc copilot environment]. Secrets and variables come from the repo's Agents settings [doc copilot environment, linked page].
- **Web and browser.** Internet is limited by a firewall by default: GitHub hosts plus a recommended allowlist of package registries, OS mirrors and CAs; blocked requests are reported on the PR. The firewall covers only processes the agent starts through its Bash tool, not MCP servers or setup steps [doc firewall]. The **Playwright MCP server is on by default**, as is the GitHub MCP server [doc copilot about, "Customizing"].
- **What loads.** Repository instructions: `.github/copilot-instructions.md`, path-specific `.github/instructions/*.instructions.md`, any `AGENTS.md` (the nearest wins), or a single root `CLAUDE.md` or `GEMINI.md` [doc repository instructions]. Organization instructions apply to the cloud agent; **personal instructions don't** ("only supported for GitHub Copilot Chat in GitHub") [doc response customization]. Skills: project skills in `.github/skills`, `.claude/skills` or `.agents/skills`, and personal skills "in your local home directory" (`~/.copilot/skills`, `~/.agents/skills`); skills "work with Copilot cloud agent" [doc copilot skills]. Also custom agents, hooks, repository MCP settings, and Copilot Memory (Pro, Pro+, Max, preview) [doc copilot about]. **Unverified:** whether setup steps that write into `~/.copilot/skills` or `~/.agents/skills` on the runner make personal skills load. The steps "will be executed in GitHub Actions before Copilot starts working" on the same ephemeral environment [doc copilot environment], but every page that names personal skills places them "in your local home directory" and none says whether the cloud agent scans the runner's home [doc copilot skills; doc adding skills; doc cheat sheet]. The dependable route is project skills in `.agents/skills`, which the cloud agent does load.
- **GitHub.** Native. It pushes to exactly one branch: a new `copilot/…` branch, or the PR's own branch when triggered by `@copilot` on a pull request; it "cannot directly run `git push`", can't mark its draft PR ready, approve or merge; workflows on its PRs wait for **Approve and run workflows** unless configured otherwise [doc copilot risks]. One repository and one PR per task [doc copilot about]. Commits are authored by Copilot, co-authored by the person who started it, signed, and link to the session log [doc copilot manage].
- **Starting it.** Agents tab or panel on GitHub, assigning an issue to Copilot, `@copilot` on a PR, Copilot Chat, a failing Actions run, GitHub Mobile, VS Code, JetBrains, Eclipse, Visual Studio, Slack, Teams, Jira, Linear, Azure Boards, Raycast, the GitHub MCP server, automations [doc starting sessions]. **For a local agent:** `gh agent-task create "prompt" [--base BRANCH] [--repo OWNER/REPO] [--follow]` (GitHub CLI 2.80.0+, public preview) [doc copilot cli], or `POST https://api.github.com/agents/repos/{owner}/{repo}/tasks` with `prompt`, `base_ref`, `model`, `create_pull_request` and a user token (public preview) [doc REST API]. The Copilot CLI's `/delegate` or `&` prefix does the same from an interactive session [doc cli delegation].
- **Long work.** Custom agents specialise it; "Deep research, planning, and iterating … before creating a pull request" on GitHub.com [doc copilot about]. The 59-minute cap means a long effort must be split into tasks [doc copilot about]. **Unverified:** whether a session can start sub-agents.
- **Watching and answering.** Agents page with session log, token usage and length; **steer** a running session by typing in the prompt box (applied after the current tool call), stop or archive it [doc copilot manage]. From a shell: `gh agent-task list`, `gh agent-task view <PR> --log --follow` [doc copilot cli]; answer with an `@copilot` comment on the PR, which works from `gh pr comment`. When done it requests the starter's review, which sends a GitHub notification [doc using on GitHub]. **No steering from a shell:** `gh agent-task` has only `create`, `list` and `view` [doc copilot cli; src cli/cli `agent_task.go`]; the REST API has only list, start and get (tasks report `queued`, `in_progress`, `completed`, `failed`, `idle`, `waiting_for_user`, `timed_out` or `cancelled`) [doc copilot REST reference; doc REST API]; the GitHub MCP server can assign Copilot to an issue (`assign_copilot_to_issue`, with `base_ref` and extra instructions) and request a Copilot review, but not steer [src github-mcp-server `copilot.go`]. So a local agent answers with an `@copilot` PR comment, which starts a new session on the PR's branch.
- **Moving it.** Check out the `copilot/…` branch; Copilot pushes to the PR branch by default when asked on a PR [doc using on GitHub]. Local to cloud: Copilot CLI `/delegate` commits unstaged changes to a new branch first [doc cli delegation].
- **Cost and limits.** "Available for all paid Copilot plans": Pro $10/month (1,000 base AI credits), Pro+ $39, Max $100, Business $19/seat, Enterprise $39/seat [doc copilot about; doc plans]. It uses **GitHub Actions minutes and AI credits**; steering messages cost AI credits too [doc copilot about; doc copilot manage]. **Actions minutes on a public repository:** "GitHub Actions usage is **free** for **self-hosted runners** and for **public repositories** that use standard GitHub-hosted runners" [doc actions billing], and "By default, Copilot works in a standard GitHub Actions runner" [doc copilot environment]. The legacy billing page says the agent's minutes "come from your account's monthly allowance of free minutes for GitHub-hosted runners … shared with all GitHub Actions workflows" [doc copilot legacy billing], so it's billed as ordinary Actions use, and the rule has no exception for the agent. The same public-repo rule was restated for Copilot code review ("public repositories, where Actions minutes remain free") [blog code review minutes]. No page states it for the cloud agent in so many words, so the synthesis should treat it as the documented rule rather than a quoted promise; AI credits are charged either way, and the free rule names standard runners only, so a larger runner isn't covered.
- **Also on GitHub:** third-party agents, **Anthropic Claude and OpenAI Codex**, can be started from the same Agents tab, issues and `@AGENT_NAME` PR comments, "subject to the same security protections, mitigations, and limitations" (public preview, paid Copilot plans) [doc third-party agents]. How that compares with Claude Code's own cloud is for [cloud-agents-claude-code.md](cloud-agents-claude-code.md) and the synthesis.

## 4. opencode: no hosted cloud agent

**No.** opencode's docs list no hosted agent runtime [doc [opencode docs index](https://opencode.ai/docs/)]. What exists:

- **GitHub integration:** a workflow in the repo's own GitHub Actions; "Mention `/opencode` or `/oc` in your comment, and OpenCode will execute tasks within your GitHub Actions runner" (`ubuntu-latest`); it can create a branch and open a PR, and runs on comments, issues, PRs, `schedule` and `workflow_dispatch` [doc [opencode GitHub](https://opencode.ai/docs/github/)]. The compute is the user's Actions minutes, not opencode's.

- **Zen and Go** are model subscriptions, not runtimes ("OpenCode Go … access to popular open coding models") [doc [opencode Go](https://opencode.ai/docs/go/)].
- A third-party `opencolin/opencode-cloud` repository exists and isn't from the opencode project (the official repository is `anomalyco/opencode`, homepage `opencode.ai`) [src: repository metadata].

## 6. Other widely adopted cloud coding agents (brief)

None of these clearly beats Codex, Cursor or Copilot on what the maintainer needs (user-level skills and repo instructions, push and PR, started and watched by a local agent), so each gets a short entry. The follow-up found two that come close on specific points: Devin, whose documented handoff lets Claude Code or Codex start, poll and message a cloud session (§6.2), and Amp, whose orbs carry hosted personal skills and have no run cap (§6.3).

### 6.1 Google Jules

Runs each task in "a virtual machine where it clones your code, installs dependencies, and modifies files": ephemeral Ubuntu VMs with Node, Python, Go, Java, Rust, Docker and more preinstalled, a setup script, and "Run and Snapshot" to cache the result [doc [Jules docs](https://jules.google/docs), [environment](https://jules.google/docs/environment/)]. Reads the root `AGENTS.md` [doc Jules docs]. Asks you to approve a plan, takes feedback in its chat while working, and pushes a branch you can open a PR from; labelling a GitHub issue `jules` starts a task that ends in a PR [doc [running tasks](https://jules.google/docs/running-tasks/)]. From a shell: `jules remote new --repo <repo> --session "<prompt>" [--parallel N]`, `jules remote list --session`, `jules remote pull --session <id>`, and a REST API [doc [CLI reference](https://jules.google/docs/cli/reference)]. Free: 15 tasks per rolling 24 h, 3 at once; Pro 100 and 15; Ultra 300 and 60; no per-task time limit stated [doc [usage limits](https://jules.google/docs/usage-limits/)]. The VM has internet access ("a secure, cloud-based virtual machine (VM) with internet access") [doc [FAQ](https://jules.google/docs/faq/)]. The REST API answers a running session: `POST https://jules.googleapis.com/v1alpha/sessions/{id}:sendMessage`, `:approvePlan`, `GET …/activities`, and `automationMode: AUTO_CREATE_PR` on create [doc [API reference](https://jules.google/docs/api/reference/)]. MCP servers (Linear, Stitch, Neon, Tinybird, Context7, Supabase) since 2026-02-02 [blog [changelog](https://jules.google/docs/changelog/)]. Unverified: skills (neither docs nor changelog mention them).

### 6.2 Devin (Cognition)

Each session gets a VM with a shell, an IDE and a browser [doc [Devin docs](https://docs.devin.ai/)]; environments are built from "blueprints", with Linux, macOS and Windows VMs available [doc [Devin llms.txt index](https://docs.devin.ai/llms.txt)]. Reads `AGENTS.md`, injecting the first 16 KiB [doc [AGENTS.md for Devin](https://docs.devin.ai/onboard-devin/agents-md)]. Opens PRs and answers review comments through its GitHub integration [doc index, "Devin GitHub integration"]. Started from web, Slack, Teams, Linear, or the API (`POST https://api.devin.ai/v3/organizations/$DEVIN_ORG_ID/sessions`) [doc [API overview](https://docs.devin.ai/api-reference/overview)]. Devin Outposts runs sessions on your own machines [doc index].

**Handoff from Claude Code or Codex.** Devin's official handoff comes in two forms [doc [Hand off to Devin Cloud](https://docs.devin.ai/work-with-devin/devin-handoff); doc [CLI handoff](https://docs.devin.ai/cli/handoff)]. Its own local agent, the Devin CLI, has `/handoff`, which sends the conversation, current branch and uncommitted diff to a new cloud session; in reverse, `/handoff` or `/pickup` in a cloud session checks out its PR branch locally. For Claude Code, Codex, Cursor or any shell there is **Devin Handoff** (`club-cog/devin-handoff`, MIT, installed as `devin-handoff@cognition` and linked from Devin's docs): a Claude Code plugin (`/plugin marketplace add club-cog/devin-handoff`, `/plugin install devin-handoff@cognition`), a Codex plugin (`codex plugin add devin-handoff@cognition`), or a plain `SKILL.md` plus `devin-handoff.sh`, with a `DEVIN_API_KEY` in the environment [src devin-handoff README at `24a60e0`]. **Start:** the agent runs `devin-handoff.sh create --task … [--context …]`, which reads the repo and branch from `git remote` and `git rev-parse`, adds `git diff HEAD` (truncated to 100 KB) and whatever the agent has learned, creates a session tagged `handoff` through the Sessions API, and prints the session URL. **Watch:** `devin-handoff.sh poll <id> [--interval N] [--archive]` calls `GET /sessions/{id}` until Devin "finishes or is waiting on a message from you". **Hear back and answer:** the result is a PR through the GitHub integration; a local agent can send a message with `POST /v3/organizations/{org_id}/sessions/{devin_id}/messages` ("Send a message to an active session. The session will be automatically resumed if suspended.") [doc [Send message](https://docs.devin.ai/api-reference/v3/sessions/post-organizations-sessions-messages)] or the Devin MCP server's `devin_session_interact` (status, send messages, read messages) and `devin_session_gather` (wait for several sessions to settle) [doc [Devin MCP](https://docs.devin.ai/work-with-devin/devin-mcp)]; the Devin CLI also streams and steers one with `devin --cloud -p "…"` and `devin --cloud -r <url>` [doc [Devin Cloud in the CLI](https://docs.devin.ai/cli/cloud)]. **Pricing:** Free (limited use), Pro $20/month and Max $200/month (single user), Teams from $80/month ($40 full seats, free flex seats on shared credits); paid plans carry daily and weekly quotas shared by cloud sessions, the Devin CLI and Devin Desktop, with prepaid on-demand credits past the quota [doc [self-serve plans](https://docs.devin.ai/admin/billing/self-serve)]. Personal API keys (`apk_`) use the v1 API; service keys (`cog_`) use v3 [src devin-handoff README].

**User skills.** Devin reads `SKILL.md` files only from repositories, not from a home folder, but "Devin's backend indexes `SKILL.md` files across all repositories connected to your organization", available "before any repos are cloned", in `.agents/skills`, `.devin/skills`, `.github/skills`, `.claude/skills`, `.cognition/skills` or `.windsurf/skills` [doc [Devin Skills](https://docs.devin.ai/product-guides/skills)]. A skills repository connected to Devin would therefore serve its skills to every session, if they sit under one of those paths (this repo keeps them under `skills/`, which isn't one).

### 6.3 Amp (orbs)

Since 2026-06-30, "you can now launch Amp agents remotely in orbs": machines with "your code, plugins, and tools", billed by the minute, asleep when idle. `amp -ox "<prompt>"` spawns a thread in an orb from the terminal, the TUI can do the same, and `amp sync <thread>` syncs its changes to the local machine; threads can be watched from web and phone [blog [Agents in Orbs](https://ampcode.com/news/agents-in-orbs)]. **Sizes:** `a1.tiny` 1 CPU/2 GB ($0.08/h) to `a1.xxlarge` 16 CPU/32 GB ($1.32/h), `a1.3xlarge` 16 CPU/44 GB ($2.13/h) for top tiers, all with 60 GB disk; default `a1.medium` (4 CPU/8 GB, $0.33/h); `--orb-size` per thread. **No run cap:** an orb pauses 5 minutes after the agent's last work or 20 minutes after your last interaction, whichever is later; "These are idle timeouts, not a limit on how long an orb can run" [doc [Sizes & Costs](https://ampcode.com/docs/orbs/sizes-and-costs)]. 20 orbs in a burst, then one every five minutes; the agent can "spawn browsers"; a shared tmux terminal; the macOS and iOS apps notify when a thread wants the next message [doc [Orbs](https://ampcode.com/docs/orbs)]. `.agents/setup` (stopped after 20 minutes) and `.agents/resume` customise the machine; snapshots are reused for up to 72 hours [doc [Customizing Orbs](https://ampcode.com/docs/orbs/customizing)]. **Git:** the **Ship** button by default commits, rebases on the base branch, runs tests and pushes straight to the base branch; **Push to Branch** pushes a feature branch and, on GitHub, reports the PR URL; **Custom Ship** runs your own prompt [doc [Shipping Changes](https://ampcode.com/docs/orbs/shipping)]. **Instructions and skills:** `AGENTS.md` from the working directory and its parents, plus a personal "Global AGENTS.md" edited in the web settings [doc [AGENTS.md](https://ampcode.com/docs/customize/agents-md)]; personal and workspace skills are stored by Amp in Git repositories and are "global because they are not tied to one project or machine" [doc [Global Plugins & Skills](https://ampcode.com/docs/customize/global-plugins-and-skills)].

### 6.4 Factory (Droids)

Droid Computers are persistent environments that keep packages, files and services between sessions: Managed ones on Factory's cloud (4 CPU, 8 GB RAM, 6 GB swap, pause on idle), or Bring Your Own Machine, "such as a VPS, workstation, or on-prem server"; sessions target a computer from the Factory App's **Computer** tab or from Slack; the CLI lists computers, registers a machine (`droid computer register`) and opens SSH or port forwards (`droid computer ssh`, `port-forward`); a managed computer runs Droid as a `factory-user` account with sudo [doc [Droid Computers](https://docs.factory.ai/droid-computers/overview)]. Droid reads `AGENTS.md` and personal instructions from `~/.factory/`, `~/.agents/` or `~/.agent/` [doc [AGENTS.md](https://docs.factory.ai/harness/agents-md)], and personal skills from `~/.factory/skills/<name>/SKILL.md` "on your machine" [doc [Skills](https://docs.factory.ai/harness/skills)]; because a Droid Computer keeps its files between sessions, skills placed in its home folder should persist (inferred, not stated). Individual plans: Pro $20/month, Plus $100, Max $200 [doc [Individual Plans](https://docs.factory.ai/pricing/individuals)]. Unverified: PR creation from a Droid Computer session and starting one from the CLI or API.

### 6.5 OpenHands Cloud

The hosted version of the open-source OpenHands agent, running each task in a hosted sandbox. Labelling an issue `openhands` or mentioning `@openhands` makes it comment and "open a pull request if it determines that the issue has been successfully resolved"; `@openhands` on PRs works when both sides are repositories you added; it uses 8-hour scoped tokens [doc [OpenHands GitHub installation](https://docs.openhands.dev/openhands/usage/cloud/github-installation)]. From a shell: `openhands cloud -t "<task>"` after `openhands login` [doc [CLI: OpenHands Cloud](https://docs.openhands.dev/openhands/usage/cli/cloud)], or `POST https://app.all-hands.dev/api/v1/app-conversations` with an `initial_message`, then poll `GET …/app-conversations?ids=…` for `sandbox_status` and `execution_status` (a start task passes through `SETTING_UP_SKILLS`) [doc [Cloud API](https://docs.openhands.dev/openhands/usage/cloud/cloud-api)]. Repo guidance lives in `AGENTS.md` [doc [General Skills](https://docs.openhands.dev/overview/skills/repo)]; the Cloud `/launch` route opens a conversation with plugins or skills from a Git repository [doc [Plugin Launcher](https://docs.openhands.dev/openhands/usage/cloud/plugin-launcher)]. Pricing: a free Individual tier ("Bring your own key or use our providers at-cost", 10 conversations a day) and custom-priced Enterprise [doc [pricing](https://openhands.dev/pricing)]. Unverified: sandbox size and limits, and sending a follow-up through the API.

10. **Smaller agents:** Jules skills; Factory PR creation and starting a Droid Computer session from the CLI or API; OpenHands sandbox size and follow-ups through the API. None is documented; only worth a trial if the synthesis picks one of them.
