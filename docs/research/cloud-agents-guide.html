3Eight words

The few terms the research leans on

You'll meet these in every file. Each one in plain language, with where it shows up here.

Effort
One piece of work described by a spec and split into tickets, delivered as one pull request.This research is an effort: spec #45 and its tickets.
Orchestrator and delegate
The orchestrator runs an effort: it hands each ticket to a delegate, collects each delegate's commit, and opens the pull request. A delegate does one ticket and reports back.Hosted agents like Codex fit the delegate role, not the orchestrator's.
Handover
One session passing work to a new session: it writes a handoff file, commits and pushes it, then starts the new session with a one-line prompt pointing at it.The open question is how to start that new session somewhere other than the Mac.
Worktree
A second working copy of the same repository on its own branch, so several agents can work side by side without touching each other's files. Treehouse makes them on the Mac.The VPS has plain git but no Treehouse yet.
Herdr
A terminal multiplexer built for coding agents: workspaces, tabs and panes, each able to hold an agent you can list, read and prompt. It can save another machine and drive it.Version 0.9.2 adds herdr --machine, which the plan builds on.
VPS
A virtual private server: a small Linux machine rented by the month that stays on when your laptop is closed. Yours is Hetzner's smallest shared tier, 2 vCPU and 4 GB.It already runs Claude Code in Herdr.
Cloud session
A Claude Code session that runs on Anthropic's machines instead of yours. Each one gets a fresh virtual machine, keeps running with the laptop closed, and is reclaimed when idle.Started from claude.ai, the phone, the Desktop app or claude --cloud.
Routine
A saved Claude Code setup (a prompt, repositories, connectors) that runs as a cloud session on a schedule, an API call or a GitHub event. A research preview.Its API trigger is the one documented way for an agent to start cloud work; a cloud session also has a create_session tool, untested.

5What we found

Seven findings, one line each

  1. The Mac stays home. It's the only place with every harness, current skills, Treehouse, a browser and a working notification. Nothing researched beats it for an orchestrated effort today. Synthesis

  2. The VPS is one upgrade away. Web, GitHub and Claude Code already work there; it needs Herdr 0.9.2, your current skills, a worktree tool and a way to notify you. VPS file

  3. Claude Code's cloud is good for tasks, and close to ready for efforts. Tested from inside: it pushes a branch it names, opens pull requests, and has a headless Chromium. Your skills load once a setup script installs them into the VM's home; idle VMs still lose background work, sub-agents can't nest, and an agent-side start is untested. Probe file

  4. Other hosted agents are delegates, not orchestrators. Codex, Cursor and Copilot each take one prompt on one branch and return a pull request; none is worth a sign-up before Claude Code's cloud is tried. Providers file

  5. Managed Agents is a developer API, not a better cloud session. It bills API tokens plus session-hours on top of the plan and drops CLAUDE.md, skills, hooks and the Agent tool. Its one draw is a self-hosted sandbox on the VPS, worth only a budget-capped trial. Managed Agents file

  6. On the VPS, RAM is the limit, not CPU. With no swap, running out of memory kills processes; the next tier up costs €3 more a month, but Hetzner may refuse the rescale for now. Sizing file

  7. Firstmate is worth borrowing from, not adopting. Take its status file per worker, its readiness check before handing work to another machine, and its rule that an unreachable machine is unknown, never a reason to fail over. Firstmate file

The first pass left one gap: no first-hand facts about the cloud VM, because both of its cloud probes, run from an agent's shell, came back empty. That gap is closed. Your own claude --cloud "say hi" started a session, and #78 tested the cloud from inside it; where it contradicted the docs, the cloud files now say so.

6Your questions, answered

The questions the spec started from, answered here

Spec #45 asked 28 questions. Here they are in four groups, a line or two each. Open a group to read it; the links underneath are only for when you're curious.

Questions 1-11Claude Code's cloud sessions
What machine does it run on?
A fresh Ubuntu 24.04 VM for each session: 4 vCPU, 15.7 GiB of RAM, 30 GB of writable disk, running as root. It's reclaimed when idle, and only what was pushed and the conversation survive. first-hand
Which tools, and can it install more?
A broad toolchain, but no gh CLI. The environment's setup script runs as root before the session starts and is cached, so it can install anything.
Can it reach the web and drive a browser?
Web goes through an allowlist ("Trusted") by default; each environment can switch to Full or Custom. WebFetch obeys the list and WebSearch works. A headless Chromium is pre-installed and works once it trusts the network proxy's certificate. first-hand
Does my setup load there?
Yes: the repo's CLAUDE.md (and so AGENTS.md), the repo's .claude/skills, and skills enabled on your claude.ai account. Only with one repository: repo hooks, permission rules and .mcp.json. No: anything in your laptop's ~/.claude (global instructions, skills, hooks, your own MCP servers). The way in: skills placed in the VM's own ~/.claude/skills load, even mid-session, so a setup script can carry yours (D6).
GitHub: which branch, can it push and open a PR?
It starts on the branch you started it from and can push there, to its own claude/… branch, or to a new branch it names. Pushing to an existing branch made elsewhere is untested (E20). It opens pull requests with its Create PR button or GitHub tools. GitHub's REST API works for the attached repo; GraphQL is blocked. first-hand
How is it started, and can a local agent start one?
You can start one from claude.ai, the phone, the Desktop app, or claude --cloud "task" in a terminal, which prints the session's URL and exits. From an agent: a routine's API trigger is the documented way. claude --cloud from an agent's shell and create_session from inside a cloud session are untested (E11, E17).
Can it run a whole effort with sub-agents?
Partly. Sub-agents work, but only one level deep. Background work dies when an idle VM is reclaimed, and a permission prompt stalls an unattended run. The first shape to try is a single-session effort you watch, once the skills load (E16). Claude Code projects add a coordinator that runs threads in parallel.
How do I watch it, answer it and hear from it?
Watch and answer on claude.ai or in the Claude app. claude -p "<msg>" --cloud <id> sends a follow-up from any machine. No CLI command prints its status, but from inside a cloud session list_sessions reads every session on your account. For done-or-blocked, the pull request is the signal today; the session's own phone push is half tested (#80).
Can it come back to my machine?
claude --teleport <id> pulls its branch and conversation into a local checkout, as a copy. The docs don't say the cloud original stops (E12).
What does it cost?
Plan usage, with no charge for the VM. The one-time promo credit is spent first, and you saw it go down after #78's session. Routines have a daily run cap.
Scheduled or triggered agents?
Routines: a saved prompt, repositories and connectors that run as a cloud session on a schedule, an API call or a GitHub event. They're a research preview. A new routine gets every connected connector, with write access, by default, so review them.

  5. D13What to take from Firstmate?You: don't adopt it; understand it and pick what to borrow. Research #88 is in: 18 ideas ranked, the top two small changes to your skills.Needs more

    What it is. An open-source "agent distro" by Treehouse's author: you clone it, start any terminal agent inside it, and that agent becomes your one point of contact for every project.

    Captain and first mate
    You're the captain; you talk only to the first mate, one long-lived agent per machine that never writes code itself.
    Crewmates
    One visible terminal agent per task, each in its own worktree and branch, started from a written brief.
    Brief on disk
    The task's intent, spec, rules and definition of done, as a file. If a crewmate dies, a new one starts from the same brief.
    Status file
    Each crewmate appends one-line events (working, needs-decision, blocked, done) to a file. A decision stays open until a matching resolved line.
    Inbox and doorbell
    Messages to a crewmate go into files it acknowledges, not pasted keystrokes, so none are lost.
    Watcher
    A bash loop with no tokens spent checks every 15 seconds, and wakes the first mate only when something needs it.
    Secondmates
    A whole Firstmate home on another machine over SSH, with a readiness "doctor". If it's unreachable, its state is unknown, and work never silently fails over to the local machine.

An isolation check first; a branch; work; a status line only for a phase change; read the inbox at checkpoints and when the doorbell rings; each turn end touches a file the watcher reads.
Decisions
The worker writes needs-decision and stops. The first mate decides what's unambiguous, and escalates only a scope expansion, a product call or destructive work. It holds the item for you and relays your answer with --resolve-key.
Delivery and merge
"Done" counts only when the head is pushed. The PR is registered and polled; the merge waits for your word, then checks live state and merges with --match-head-commit, so a push after your review fails the merge.
Teardown
Refuse if anything isn't landed; close the tab; return the worktree; mark the item Done. The brief and any report stay.
Crash and restart
A new session takes a lock or stays read-only, then reconciles from the meta records, status logs and wake queue. A stuck worker is peeked, answered, interrupted, then relaunched into the same worktree with the same brief plus a progress note. "A restart must be a non-event."
Remote secondmates
Seed a home on the host after a readiness check; every call is a validated script run over SSH; requests go into the remote inbox with a correlation id; replies are mirrored back from its status file; an unreachable host reads unknown.
