# Decisions: set-up-machine

The decisions behind the `set-up-machine` skill. This file is for maintaining it and is never installed. Add an entry for each new decision: the date, what was decided, and why. The spec is "Spec: every harness and project is set up and audited from the skills" (#49).

## 2026-10-01: retain the occupied caller at settlement

- **The session-host fallback keeps the caller and its occupied worktree open.** Remove the example that hands the user an own-worktree release command: it contradicts the settlement decisions in [Workflow: Make Herdr and Treehouse settlement reliable without closing topology](https://github.com/yahyabedirhan/skills/issues/123). This changes the source role guidance only; machine reconciliation remains a post-merge follow-up.

## 2026-09-29

- **The rule table is JSON.** The reconcile script and the later pre-tool hook read it with Python 3's standard library, and macOS ships Python 3.9, which has no TOML reader (`tomllib` is 3.11+).
- **A row describes a command by its meaning, not by native patterns.** `match` names the program and the flag groups it carries; each adapter expands that into its own native form (Claude Code: one `Bash(<prefix>:*)` per flag order, spelling and `/bin/`, `/usr/bin/` path). One row then serves Claude Code's text matching, Codex's token prefixes and the hook's normalised matching, and none of them is the source.
- **The shared global instructions file is `~/.config/agents/AGENTS.md`.** It sits in no harness's own folder, so no harness update or reinstall overwrites it, and `~/.config` is the usual place for user config on Linux, the VPS's system. `AGENTS.md` is the name Codex and opencode read, so their adapters can link to it directly. `~/.agents/` was the other candidate; it belongs to the `skills` CLI, which owns what's in it.
- **Claude Code reaches it by an `@` import line in `~/.claude/CLAUDE.md`.** Claude Code has no global `AGENTS.md`, and imports in user-scope files load without approval. The adapter adds only that line, since the rest of that file is rewritten under its own ticket.
- **The skill owns a marked block in the shared file, and nothing outside it.** The rule lines are regenerated between `set-up-machine:rules` markers, so the file can also hold the person's own workflow without the skill ever touching it.
- **What the skill wrote is recorded in a manifest beside the shared file** (`~/.config/agents/set-up-machine.json`). That's what makes "never remove or loosen an entry it didn't write" checkable: an entry is the skill's only if the manifest names it, and only those are removed when the table drops them. An entry that was already on the machine when the skill arrived stays the user's, even when it matches the table.
- **Tightening adds, never moves.** Claude Code checks deny before ask before allow, so adding the stricter entry is enough; removing the looser one would remove an entry the skill didn't write.
- **Apply takes the plan's id.** The id is a hash of every write the plan would make, so apply writes exactly the diff the user approved, and refuses if anything changed in between. That keeps "one approval" honest when time passes between plan and apply.
- **Every step takes `--home`.** Tests, and any trial of a table change, run against a copy of the home folder; the real machine changes only through a plan the user approved.
- **Extras and gaps are reported, not changed.** A rule on the machine that the table lacks is listed as `extra` so the table can grow from it; what a harness can't express is listed as a `gap` so no one reads it as enforced.
- **Checking a live session needs the real login.** A session pointed at a copied config folder (`CLAUDE_CONFIG_DIR`, or `HOME`) isn't logged in, so the end-to-end check of the rule line reaching a session runs after the real apply. Before it, `claude -p --setting-sources project,local --settings <copied settings.json>` proves the generated deny entries refuse `rm -rf` and its variants.

## 2026-09-29: the full rule table (#53)

- **`match` has three kinds, told apart by their keys:** a command (`program`, `subcommands`, `flags`, `operands`), a file (`paths`, `access`) and an MCP tool (`server`, `tool` regexes). Each still says what a rule covers by meaning, so the Claude Code adapter, the other harnesses' adapters and the pre-tool hook read the same row with the standard library.
- **Rows group a family, not one command.** `gh repo delete`, `archive`, `unarchive` and `rename` are one row, so the shared file gets one line per meaning rather than one per command. The families are today's Claude Code deny list, read by meaning; a command pattern that named one account (a connector ID) isn't carried over.
- **`zsh -c` joins `bash -c` and `sh -c`.** The spec names all three as ways around the `rm -rf` rule.
- **Writes to `.env` and `secrets/` are `Edit(...)` rules.** Claude Code accepts `Write(...)` rules and never checks them; a probe with only `Write` denies let every write through, and one with only `Edit` denies refused them. An old `Write(...)` entry is reported as an extra that does nothing, and kept, since the skill didn't write it.
- **Secret paths reach every folder (`**/.env`), not only the working directory.** A probe confirmed `./**/.env` refuses both `.env` and `sub/.env`. The old root-only entries are listed as extras.
- **Mail tools are matched against the harness's own tool list, found at plan time.** Their names depend on how a connector is attached (a claude.ai connector is `mcp__claude_ai_<Name>__…` in the CLI), and only the running harness knows. The table stores the meaning (a server containing `mail`, tools starting `send`, `reply`, `forward`, `trash`, …); a glob like `mcp__*__send_message` would also catch unrelated servers' tools of the same name. The Claude Code adapter reads the list from a `claude -p` session's `init` event and stops it before the model is called. When the list can't be read, the entries written before stay.
- **`allow-and-report` rows get a native `allow`.** The report half comes from the pre-tool hook, which reads this same table.
- **A stricter entry on the machine is reported, not replaced.** Where the machine denies what the table asks for (today's `git push --force-with-lease` and `gh repo edit`), the plan lists it as `stricter`; getting the table's level means the user removing that entry by hand.
- **A broader entry counts as present.** `Bash(gh repo delete*)` already covers `Bash(gh repo delete:*)`, so the adapter doesn't add a duplicate or list the broader one as extra.

## 2026-09-29: the pre-tool hook (#54)

- **The hook imports the setupmachine package** rather than being one self-contained file. It ships in the same skill folder, so the import always resolves, and it reads rows through `rules.py`, the same loader the adapters use, so a row can't mean one thing to the plan and another to the hook. Its core takes a harness-neutral `ToolCall` and returns denials and reports; each harness has a reader and a writer in `hook.HARNESSES`, so Codex, opencode and Cursor add a pair, not a copy.
- **It reads a command the way the shell runs it, not as text.** Split into simple commands, wrappers and assignments dropped, programs by basename (`mkfs` covers `mkfs.ext4`), flags read anywhere until `--` and matched per group, subcommands found anywhere in the words (`git -C dir push`). Shell strings, `eval`, `sudo`, `xargs`, `find -exec`, command substitutions, heredocs and here-strings fed to a shell, and `echo … | sh` are read as commands of their own. Heredoc bodies fed to anything else (a commit message) are skipped, so writing *about* `rm -rf` isn't refused.
- **Allow-and-report prints nothing.** An `allow` answer would skip Claude Code's native permission check, deny rules included. The hook logs the call and stays silent, and the native `allow` entry lets it run.
- **A deny anywhere in the call wins, and then nothing is reported.** The call doesn't run, so there's nothing to report.
- **The hook fails open.** If the input or the table can't be read, it exits 1, a non-blocking error in Claude Code, and the native deny entries underneath still refuse. A hook that failed closed would stop every tool call on a broken table.
- **The hook also checks file and MCP-tool rows.** File tools against the path globs (a read rule also covers writes, as Claude Code's `Read` deny does), and MCP tools against the row's regexes at call time, which covers a mail tool connected after the last plan.
- **The report folder is configured in `~/.config/agents/hook.json` (`report_dir`)**, beside the manifest. The plan creates it once with `~/.local/state/agents/reports` (the XDG state folder, since reports are state, not config) and never rewrites it. Against another `--home` the wired command names that home's config file, and the default folder sits inside that home. Reports are one JSON line per call in one file per UTC day.
- **The hook is wired for every tool (`*`).** It checks commands, files and MCP tools, and a new tool is covered without a new plan. Python's start-up is the cost, a few tens of milliseconds per call.
- **The hook's gaps are listed once, in its plan section,** not repeated on each command row; deny and allow-and-report command rows no longer carry a per-row gap.
- **The hook reads the table the plan used.** A plan run with `--rules <file>` wires the hook with `--rules <file>`; with the skill's own table the command stays short.

## 2026-09-29: role names are the placeholders (#59)

- **The Defaults rows are named in kebab-case, the same as the placeholders skills use.** `session-host`, `worktree-tool`, `notification-method`, `agent-to-start`, `skills-repo` and `path-to-skills-repo` (the old "Skills repo" row, which held both the repo and its clone, split in two, as `maintain-environment` already used two placeholders). A skill's `<session-host>` then reads its value from the row of the same name, with nothing to translate. A file written before the rename keeps its old rows; the next apply adds the new ones as `none`, and the user moves the values across.
- **A project's own Defaults table overrides the global one for that project.** Both are in the agent's context, so the reference and the table's intro say so, and a skill's Parameters section repeats it once.

## 2026-09-29: agents never read environment variables (#64)

- **The env-var family is six rows**, since a row has one command shape: `.env` reads and writes (file rows), `cat`/`less`/`head`/`tail`/`grep`/`source`/`.` on a `.env` file, `env`/`export`/`set` on their own, `printenv` in any form, and `export -p`/`declare -p`/`typeset -p`. `.env` moved out of the `secret-files` rows, which now hold `secrets/` only. `declare -p` and `typeset -p` join `export -p`: they list the same variables.
- **Three table fields make that expressible, each read the same by every adapter and the hook:** `arguments: "none"` (the program alone; the hook reads a wrapper that runs no command as itself, so `env -u X` is `env` and `env FOO=1 cmd` stays allowed), `files` on a command row (an operand matching the globs), and `except` on either (the globs left out). A row's `gap` names what no harness catches, and every adapter prints it.
- **`.env.example` stays open, through positive globs.** A probe showed Claude Code's path globs read `[!e]` and `[^e]` as plain classes (listing `!`/`^` and `e`) and match classes case-insensitively on macOS, and it has no other negation. So `except` becomes the globs around the exception (rules.without): 15 per glob, exact for names built from letters, digits, `_` and `.`; the hook applies the exception exactly.
- **Write rows also write `Write(**/…)` entries**, for the Cursor CLI, which checks `Write` against absolute paths and so never matches `./`. They keep the plain globs (no exception): Cursor's globs have only `*` (#57 confirmed it), so a Cursor write to `.env.example` is refused.
- **`./.env.*` isn't root-only.** A probe showed `Read(./.env.*)` refuses `sub/.env.local` and `sub/.env.example`: a path with no `/` after `./` matches at any depth, as in `.gitignore`. So an existing entry like it also refuses `.env.example`; the plan names that on its `extra` line, and the user removes it by hand to open the file.
- **The `$VAR` expansion gap is named on the `printenv` row** and explained in its rule line; on Claude Code the gap line adds what the auto-mode guard covers.
- **Command rows with `files` get no Claude Code `Bash` entries.** Bash rules match text, not paths. Claude Code's Read rules already refuse `cat`, `head`, `tail` and `grep` on a denied file (probed); `less`, `source` and `.` are the hook's, named as a gap.
- **A row's `guard` goes into Claude Code's `autoMode.hard_deny`** (research: auto-mode-semantic-guard, 6.1), with `classifyAllShell: true`, in the same settings write. `$defaults` is added only when the skill creates the array; the user's other `autoMode` entries are never touched, and the manifest's `auto_mode` list names what the skill may remove. The guard's text says `.env.example` isn't an env file, since a hard deny can't be cleared and the table leaves that file open. The guard sits on the `printenv` row, the family's one row that carries a gap; the other harnesses' adapters read `rule.guard` if they gain a semantic guard.

## 2026-09-29: Codex (#55)

- **The table's rules live in their own file, `~/.codex/rules/set-up-machine.rules`, regenerated whole.** Codex loads every `*.rules` file and the strictest decision wins, so the skill never edits `default.rules`, where Codex itself saves "always allow" choices. The file holds every row, even where another file already covers it, so the table's rules and their justifications don't depend on anyone else's file staying put. On a tie in prefix length Codex shows the justification of the file that sorts last, which is this one.
- **Separate flags get one rule per order; clustered short flags share one rule of alternatives.** Prefix rules are token-exact and in order, so `rm -f -r` needs its own pattern. No `/bin/` spellings: Codex resolves an absolute program path to its basename.
- **No Codex rule for `bash -c`, `sh -c` or `zsh -c`.** Codex wraps every command in `<shell> -lc` (or `-c` with login off) and checks non-plain commands against that wrapper, so such a rule would refuse ordinary commands with a redirect or `$(…)`. The hook sees the command before the wrapper and enforces the row.
- **`allow-and-report` is `allow`.** It's Codex's no-prompt level; it also runs the command outside the sandbox, which `gh api` needs for the network anyway.
- **The plan writes the hook's trust entry.** Codex skips an untrusted user hook, and trusting it in `/hooks` would be a second approval outside the plan. The hash is reproduced from Codex's source and checked against Codex's own `hooks/list`; the plan line says approving it is that review.
- **The hook wires into `hooks.json`, not inline `[hooks]` in `config.toml`.** The file is JSON, which the standard library edits safely, and it's where Codex users already keep hooks; Codex warns when both hold hooks.
- **`~/.codex/AGENTS.md` becomes a link only when no line would be lost.** A line counts as kept when it's already in the shared file, or inside a known block an external skill replaces; otherwise the plan lists it as `extra` and leaves the file, so moving lines stays a reviewed step rather than a deletion hidden in a backup.
- **Context7 is the upstream `find-docs` skill from `upstash/context7`,** the one whose text the block copied. The plan shows the install as an `added` line with its exact `npx skills add` command, and apply runs it before writing files, with `HOME` set to the planned home so a trial installs into the trial. It follows maintain-environment's scope rule (`-g -a codex`, plus `-a claude-code` unless `~/.claude/skills` links to `~/.agents/skills`).
- **A real Codex session is checked without a login** by pointing `codex exec` at a local stand-in model that asks for one command. Copying the real `auth.json` into a trial home could refresh and rotate its token, logging the real Codex out.
- **#64's rows on Codex:** bare rows (`env` alone) and rows on files (`cat .env`) get no Codex rule, since prefix rules can say neither "nothing after it" nor "a path anywhere in the operands"; the hook enforces both, with the `.env.example` exception. A row's `gap` is printed per row, and a `guard` gets a `none` line, since Codex has no semantic guard.

## 2026-09-29: opencode (#56)

- **opencode's global `AGENTS.md` is a relative symlink to the shared file** (`../agents/AGENTS.md`). opencode doesn't follow `@` imports and reads files with a plain read, which follows links, so the shared file needs no copy. An existing `AGENTS.md` there is the user's: listed as `extra`, with the gap that opencode reads it instead, until its lines move into the shared file. It uses the same symlink write as Codex's link (`FileWrite.link_to`).
- **The adapter writes the last global config file opencode loads** (`config.json`, `opencode.json`, `opencode.jsonc`, in that order), else a new `opencode.json`. A file holding comments isn't rewritten, since the standard library can't keep them; the plan lists the rules as a gap instead, so nothing is lost without the user seeing it.
- **Entries are appended loosest first, and every check asks which rule opencode would apply.** Its last match wins, so a stricter entry must come after anything it overrides. The plan evaluates a sample of each pattern against the file's rules the way opencode does (wildcards over tool names and patterns, `findLast`) to decide present, covered, stricter or tightened, rather than comparing keys. The same pattern at a looser level is moved to the end at the table's level, since a key can't appear twice; a tool whose rules a later tool-wide entry overrides moves after it.
- **An `except` becomes an `allow` after the row's deny entries**, the way opencode's own defaults open `.env.example`; opencode's patterns have no character classes, so rules.without's globs don't apply. Where the user's own entry refuses the exception, the allow isn't added, since it would loosen that entry: the plan lists it as `stricter`, as Claude Code's adapter does for `Read(./.env.*)`.
- **Command rows with `files` get no bash pattern, and declarations only name a gap.** Patterns match text, not paths; and `export -p` ran under a matching deny in a probe, since opencode checks only plain command nodes. Both are the hook's, and the plan says so per row.
- **Mail rows match configured MCP servers, not tools.** opencode lists MCP tools only inside a session (not in `opencode debug agent` or the server's tool list), so there's nothing to write exact denies from. A matching server is a gap left to the hook, which reads a non-built-in tool name as `<server>_<tool>`, trying each `_` as the split.
- **The hook is a generated plugin, `~/.config/opencode/plugins/set-up-machine.js`**, that runs the same Python script with `--harness opencode` and throws its output. A probe showed the thrown message reaches the model unwrapped, as the tool result. It spawns the script asynchronously with a 10-second limit and fails open, as the Claude Code wiring does. A marker line on its first line says the file is the skill's; a file of that name without it is kept and the hook reported not wired.
- **No semantic guard:** each row's `guard` is named as `none` for opencode.

## 2026-09-29: Cursor (#57)

- **One adapter covers the IDE and the CLI.** They share the user rule folder and `~/.cursor/hooks.json`; only the CLI has a permission file. The plan names which half each gap belongs to.
- **The shared file reaches Cursor as a generated copy in `~/.cursor/rules/global-instructions.mdc`.** Both read user rule files there (the CLI only for a working folder inside the home folder, by walking up), an `.mdc` file applies to every chat only with `alwaysApply: true` frontmatter, and `@file` is a context reference, not an include. So neither a link nor an import works; the copy is refreshed on every apply, and an edit to the shared file shows in the plan until then. Account User Rules live on the account, out of reach, so they aren't used; whether CLI sessions get them stays unconfirmed and no longer matters.
- **The CLI's native entries are literal `Shell(<prefix>)` in `~/.cursor/cli-config.json`.** The bundle's glob escapes everything but `*`, which matches anything, `/` included, and a literal prefix matches the prefix and anything after a space: the meaning of Claude Code's ` *` rule. Rows with `arguments: "none"` become `Shell(x:)`, which matches only the bare command (probed). Rows with `files` get none: the CLI's Read rules don't bind shell commands.
- **Claude Code's entries switch from `Bash(<prefix>:*)` to `Bash(<prefix> *)`.** Claude Code reads the two the same, but the Cursor CLI, which unions `~/.claude/settings.json` into its lists where a project can't remove them, matches the `:*` form only against the bare command and the ` *` form against every use with something after it. A probe with the CLI's own deny list empty showed the ` *` entries refusing `rm -rf x`, a force push and `gh repo delete owner/x`. An old `:*` entry with a space no longer counts as covering; the ` *` entry is added beside it, and the old one is an extra.
- **The Claude Code adapter adds an empty `allow` beside a `deny`.** The CLI's schema needs both lists; without one it skips the whole file, silently.
- **The hook is wired on `beforeShellExecution`, `beforeMCPExecution`, `beforeReadFile`, and `preToolUse` for `Write|Delete|Grep`.** These are the IDE's only hard blocks, and each call reaches one of them, so no call is reported twice. MCP goes through `beforeMCPExecution` because only it carries the server name; `preToolUse` calls a tool `MCP:<tool>`.
- **The Cursor hook always answers JSON, `{}` when it lets a call through,** and puts the refusal in both `user_message` and `agent_message`. A probe showed the CLI gives the agent `user_message`, and that a hook `allow` overrides neither a native deny nor the allowlist prompt. It isn't `failClosed`, matching the Claude Code hook's fail-open decision; the gap says the IDE then has nothing underneath.
- **Claude Code's hook, run by Cursor, refuses but doesn't report.** Cursor runs the hooks in `~/.claude/settings.json` too; the payload's `cursor_version` tells the hook to leave the report to the Cursor-wired one.
- **`.env.example` is refused natively in the CLI.** With no classes an exception can't be written, and a plain `**/.env.*` refusing too much is safer than leaving `.env.local` to the hook; the hook and the IDE leave it open, and the plan names the gap.
- **Bare rows get no Claude Code entry.** An exact `Bash(env)` refuses only `env` in Claude Code, but the Cursor CLI reads `~/.claude/settings.json` and matches it as a prefix, so it would refuse `env FOO=1 cmd`, `export FOO=1` and `set -e`, which the table allows. So `env`, `export` and `set` alone are the hook's (and, in part, the auto-mode guard's) on Claude Code, named as a gap there; `cli-config.json` keeps `Shell(x:)`, which matches only the bare command. This replaces the #64 decision to write exact entries.
- **Cursor has no memory: `none` in its adapter's plan,** out of `memory.WITHOUT_MEMORY`.

## 2026-09-29: the final branch review

- **Every wired hook command fails open.** Claude Code, Codex and Cursor block a call on exit 2, which is what `python3 <script>` returns when the script is gone, so a moved or removed skill would have blocked every tool call. The command is now `[ -f <script> ] && python3 <script> … || true`, and Cursor's ends `|| echo '{}'`, since it reads an empty answer as invalid JSON, which blocks. A deny is JSON on stdout with exit 0, so it passes through. The hook's own exit 1 on an unreadable table is now silent rather than a non-blocking error the user sees; the native entries still hold. opencode's plugin checks the script exists before starting it. The plan names a hook script outside `~/.agents/skills` or `~/.claude/skills` (a repo checkout) as a gap, once, in the hook configuration section.
- **`arguments: "flags"`: a program with flags and nothing else.** Bare `declare` and `typeset` join `env-dump`, and a new row, `env-dump-listed`, refuses `declare`, `typeset` and `export` with only flags (`declare -x`, `typeset +x`), which list the variables carrying them. No harness's patterns can say "only flags" without refusing `declare -x NAME=value`, so its native entries are none and every adapter names the gap. `export -p` alone is refused by both it and `env-dump-declared`; the overlap is kept, since `-p` with a name (`declare -p TOKEN`) still needs the older row.
- **The user's own skills repo is installed as a plan item.** The spec's "shared skills installed": the plan reads the `skills-repo` Defaults row from the shared file and, when the skills CLI's lock file (`~/.agents/.skill-lock.json`) records no skill from that source, shows `npx --yes skills add <skills-repo> -g -a codex [-a claude-code] -y` as an `added` line that apply runs (maintain-environment's agent flags, the same helper as Context7's install). No value, or `none`, is a `none` line; a value that isn't `<owner>/<repo>` is a gap. Nothing is guessed.
- **The hook checks redirects and `tee` against the file rows.** A redirect's target is a read (`<`) or a write (`>`, `>>`, `&>`), and `tee`'s operands are writes; heredocs, here-strings and descriptor duplications (`>&2`) aren't files. A write is checked against the read rows too, as for file tools.
- **`operands` takes alternative sequences.** `chmod-recursive-777` lists `777`, `0777`, `a+rwx`, `a=rwx`, `ugo+rwx` and `ugo=rwx`; Codex gets one pattern with the alternatives, the other harnesses one entry per spelling. Other spellings of the same mode are the row's gap.
- **A trial `--home` never starts a real harness.** Claude Code's and Cursor's tool discovery read the real machine's config and login, so under a `--home` other than the user's own the plan skips it, names the gap and keeps the mail entries written before, unless `--tool-names` supplies the list.
- **Searches are checked by path and glob.** A `Grep` (Claude Code, Cursor) or `grep` (opencode's `include`) whose glob names a file row's files by name (`*.env`, `.env*`) is refused; a glob matching ordinary names too (`*`, `*.*`) is a search over the folder, which the hook doesn't expand, named in each adapter's file-row gap.
- **File paths fold case where program names do** (macOS, Windows), so `.ENV` meets `**/.env` there.

## 2026-09-30: references, not scripts (#81)

- **The agent sets each harness up from its reference; the adapters and the plan/apply engine are gone.** This reverses the entries above that describe adapter modules, the reconcile script, the plan id and the manifest; they stay as the record. The spec asked for one adapter per harness as a reference file, and harness formats change faster than a script frozen at one version can follow. - **Codex's check reports and never fails.** Some rows get no Codex rule by design (shell rows, bare rows, rows on files), so a `differs` line is read against references/codex.md; a `stricter` line is a user rule the diff keeps.
- **No manifest.** Without code to keep it, "never remove what it didn't write" becomes: the diff removes only memory files, a harness's own global file that becomes a link, and this skill's own wiring pointing at an old script. An entry a dropped row left behind is `extra`, for the user to remove.
- **Backups stay where they were,** `~/.config/agents/backups/<time>/`, taken by the agent before any write.
- **The agent writes Codex's `trusted_hash` as part of the approved diff,** and approving the whole diff stands in for Codex's `/hooks` review (confirmed by the maintainer). `verify.py --codex-trust-hash` computes it, so the hashing lives in one place, and verify checks the entry.
- **The auto-mode guard is optional and stays off** until the probes in #65 run. The references describe it; the diff lists each guard as `none` meanwhile.
- **The opencode plugin is a template,** `references/opencode-plugin.js`, with the hook command filled in, so the agent copies it rather than writing JavaScript.
- **`~/.config/agents/hook.json` is optional.** The hook already defaults to `~/.local/state/agents/reports`; the file is only for another folder.
- **The Linux container runs verify and the unit tests.** Without a plan/apply script there is no setup to run there, and the Codex session probes needed one; they remain described in references/codex.md.

## 2026-09-30: the hook's known bypasses (#82)

- **Quoting is read in one pass before tokenizing.** A scanner tracks single and double quotes, `$'…'`, escapes, comments, `$(…)`, backticks and `$(( ))`, so a `<<` counts as a heredoc only where the shell reads code, and a substitution inside single quotes or escaped stays text. The regexes it replaces couldn't tell quoted from unquoted text. It also reads the substitutions in an unquoted heredoc's body, a bypass the review didn't list.
- **More wrappers and shells:** `busybox`, `watch`, `setsid`, `flock`, `parallel`, `script`, `chronic`, `unbuffer` and `arch`, and `fish`, `ash`, `mksh`, `csh` and `tcsh`. `watch` and `parallel` also have their words read as one shell string, and `flock -c` and `script -c` their option's string. For Pi, every item the user writes or takes from others is an extension, so the skill, `verify.py` and the tests say "extension". Literal names keep their form: the `packages` key in `settings.json`, `pi install` and `pi list`. The maintainer asked for this in review.
- **A Pi bundle is a Pi extension.** Pi delivers extensions through `packages` in `<agent-dir>/settings.json`. The skill adds a missing source and replaces an entry for the same extension at another version. It keeps every other entry.
- **A Pi extension source fits only an entry for Pi alone.** Its `source` is Pi's own form: `npm:`, `git:` or an `https://` git URL. Claude Code and Cursor need `<plugin>@<marketplace>`, and Pi can't install that form. So one entry can't serve both, and the validator refuses each mix. A local path isn't taken, since a path doesn't name the same extension on every machine.
- **Extension identity follows Pi.** Pi treats an npm source by its name, and a git source by its host and repository path without the ref. `verify.py` uses the same identity. It prints `FAIL` for another version of a listed extension, and `extra` for a configured extension the list leaves out.
- **A changed git ref needs `pi update`.** At startup Pi installs only a missing extension, and reinstalls an npm one whose version doesn't match. It leaves an existing git checkout at its old ref: a live change from `@v0.1.0` to `@v0.2.0` stayed at `v0.1.0` until `pi update <source>` ran. `verify.py` compares the checkout's `HEAD` with the ref, read-only through `git rev-parse`. It also reads `FETCH_HEAD`, since `pi update` fetches the ref and resets to it without a local tag. A checkout at another commit is a `FAIL` that names the `pi update` command.
- **Standalone MCP servers go in `<agent-dir>/mcp.json`,** the file Pi's built-in MCP client reads. `verify.py` compares the entry as it does for Cursor. It prints a `gap` when `-builtin:mcp` turns that client off.
- **One source for Pi extensions.** `agents/pi.json` could also declare `packages`, as a Pi setting. Two lists would disagree, so a `packages` key there is a `gap` that asks the user to move it into `plugins`. The skill neither compares nor writes it.
