# Decisions: skill-recap

The decisions behind the `skill-recap` skill, and the repo's tracker setup that serves it. This file is for maintaining it and is never installed. Add an entry for each new decision: the date, what was decided, and why.

## 2026-09-28

- **Its own skill, separate from `maintain-skills`.** `maintain-skills` changes skills; the recap looks back over a session to find what should change. Folding it in would load a session audit into every install or update.
- **User-invoked only.** A recap starts when the user types `/skill-recap` (Codex: `$skill-recap`), never offered or run automatically: an audit of a whole session costs real tokens and should run when the user wants it. `disable-model-invocation: true` for Claude Code, and `agents/openai.yaml` with `allow_implicit_invocation: false` for Codex, which ignores the frontmatter flag.
- **A purpose, not a checklist.** The skill says what a recap is for and gives examples of what fits it (inefficiency, rabbit holes, wrong or stale skill content, surprises, missed triggers, rules stated only in chat, invented workarounds). A fixed checklist would find only what it lists; the first manual recap, on 2026-09-27, found five improvements of different kinds.
- **Scope: the current session and its sub-agents by default, or exactly the scope the user names.** There is no standard window. The session is already in context; sub-agents are read from their transcripts on disk, whose Claude Code layout the skill states so the recap doesn't rediscover it. The audit is the same whatever the scope.
- **Findings with evidence, ending with a verdict.** "No skill changes needed" is a valid outcome, so the recap doesn't manufacture findings. Each finding names the skill, the evidence, the cost and the opportunity, so it reads as a ticket's draft.
- **The recap files nothing; `to-tickets` does.** `to-tickets` (mattpocock/skills) is user-invoked, so the recap can't call it; it names `/to-tickets` as the user's next step, into the skills repo resolved the way `maintain-skills` resolves `<skills-repo>`. This replaced a planned filing step (issue #30, closed as superseded).
- **Findings about other people's skills are reported like any other.** Whether to fork, file upstream or drop the skill is the user's call, case by case.
- **The public-repository rule is pointed at, not restated.** It lives in the user's own agent instructions; restating it in the skill would make two copies to keep in step.
- **The repo names GitHub issues as its tracker in `AGENTS.md`, with `CLAUDE.md` importing it.** `to-tickets` expects the tracker to be in the agent's context, conventionally under an `## Agent skills` heading that `setup-matt-pocock-skills` writes. The block is inlined rather than split into `docs/agents/issue-tracker.md`, since one line says it. It names `enhancement` or `bug` as the labels, because this repo has no triage labels and `to-tickets` otherwise applies `ready-for-agent`.
- **Two prompt audits before publishing: the builder's own pass, then a fresh sub-agent per `maintain-skills`.** The building agent first ran the `claude-api` prompt audit on the skill folder as a separate pass, and its fixes were applied: the transcript layout is marked as the one Claude Code uses today, with a fallback search by session id, since it is undocumented and may move; "each session has been read" became "searched", to agree with the advice to search long transcripts rather than read them whole; "long runs of tool calls on one problem" joined the search targets, so rabbit holes are found as well as errors; the verdict is a fixed phrase ("No skill changes needed." or "<n> opportunities"), followed by the `/to-tickets` step; the purpose paragraph no longer repeats the closing line that filing is the user's. It left the numbered steps (their order is real: select, audit, report) and the line calling "No skill changes needed." a good outcome (it guards against manufactured findings). A fresh sub-agent then audited the folder as `maintain-skills` prescribes. Applied: (medium) the invocation config couldn't honour "or asking for one", resolved by the invocation decision below; (medium) the Codex pointer didn't say how a skill load shows in its sessions, so the skill now says a read of `skills/<name>/SKILL.md` is the load. Flagged and left unchanged: nested sub-agents stored flat, with their depth in `.meta.json` as `spawnDepth` (later verified correct by the branch review against a live session); the facts stated about the third-party `to-tickets` (kept; re-check them if upstream changes); the public-repository rule pointing at the user's own instructions (a settled decision above; no fallback clause added).
- **Invocation stays a hard gate, and the docs say so.** The skill keeps `disable-model-invocation: true` and `allow_implicit_invocation: false`, so only `/skill-recap` (Codex: `$skill-recap`) starts it; the docs that said the user could also start it by asking for one now name the command instead. Plain-language triggering was weighed and dropped because "never offered or run automatically" is the stronger requirement.
