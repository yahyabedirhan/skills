# Decisions: effort workflow

The decisions behind the effort skills (`init-effort`, `orchestrating`, `orchestrate-effort`, `orchestrate-with-handoff`, `handover`, `handover-to-herdr`, `close-effort`, and the `implement`, `handoff`, `to-spec` and `to-tickets` forks they rely on). This file is for maintaining those skills and is never installed. Read it before changing any of them, and add an entry for each new decision: the date, what was decided, and why. When a decision is reversed, keep the old entry and add a new one that says so.

## 2026-09-24

- **The family mirrors grilling.** `orchestrating` is the discipline, like `grilling`; the other skills are entry points that each add one thing: a start, a handoff to read, or Herdr automation.
- **A skill that another skill calls is model-invoked; a skill only the user starts is user-invoked.** A skill can't load a user-invoked one, and a prompt one agent sends another through Herdr counts as typed input. So `orchestrating`, `orchestrate-effort`, `orchestrate-with-herdr`, and the `implement` fork are model-invoked with narrow triggers; `init-effort`, `init-effort-with-herdr`, and `orchestrate-with-handoff` are user-invoked. Each user-invoked skill ships `agents/openai.yaml` with `allow_implicit_invocation: false`, because Codex ignores `disable-model-invocation`.
- **An effort is a feature, a new app, a refactor, or a re-architecture, and it gets its own branch, worktree, and pull request.** Routine data upkeep runs in the current checkout. Each project lists its own routine work in its instructions.
- **The worktree is decided at the start, not at the build.** Spec, tickets, and handoff are born on the effort's branch; creating the worktree only at build time leaves thinking artifacts on the default branch, some merged and some not. The orchestrator works wherever it finds itself.
- **Two paths: plain and Herdr.** Desktop apps can't drive Herdr or Treehouse, so `init-effort` uses the environment's own worktree feature, else `git worktree`, and its handover is a prompt the user pastes. `init-effort-with-herdr` and `orchestrate-with-herdr` automate the same steps with Treehouse and Herdr.
- **Treehouse owns worktrees, Herdr owns the view and sessions, git owns the branch.** Treehouse's pool keeps dependencies installed and refuses to destroy unfinished work; `git worktree add` and `herdr worktree create` bypass the pool, so the Herdr path never uses them. `treehouse.md` and `herdr.md` in `init-effort-with-herdr` hold the daily operations, so agents don't rediscover them from `--help`; they are the place to grow the workflow's commands, such as running builds on a remote machine later.
- **New branches don't track the default branch** (`--no-track`); the first push sets the real upstream. Otherwise "matches its remote" compares against the default branch and a bare push targets it.
- **The thinking session owns the clean ending.** It writes the handoff, commits and pushes everything, then hands over; on the Herdr path that is step 1 of `orchestrate-with-herdr`, which the thinking session runs.
- **The family writes handoffs itself, in the repository** (by convention `.handoff/<date>-<effort>.md`), committed with the spec and tickets. Matt Pocock's `handoff` skill saves to a temp folder and is user-invoked, so the family states the few requirements inline instead of calling it: the handoff is part of the effort's record, and a fresh worktree must see it.
- **The handoff names the thinking session**, so the orchestrator and later sessions can refer back to its messages.
- **The handover prompt is one shape on both paths**: `/orchestrate-with-handoff <handoff>`, the worktree and branch, and the thinking session. It is written out in `init-effort` and `orchestrate-with-herdr`, the two places a thinking session ends.
- **The thinking session stops after the handover and stays open.** On the Herdr path its tab is labelled as the thinking tab, and the new one as the orchestrator (see the tab-label entry below).
- **The agent to start is the user's preference, read from their instructions; the default is `claude`.** Other options: `codex`, `opencode`, `cursor`. Where that preference should live long-term is still open.
- **The orchestrator trusts its delegates.** A delegate builds, tests, and reviews its own ticket; the orchestrator reads the report against the acceptance criteria and doesn't redo the checks, which would repeat the delegate's work.
- **`orchestrating` doesn't prescribe how to delegate.** Delegates are sub-agents by default; an entry-point skill that wants another mechanism (such as Herdr tabs) says so itself. Delegating tickets to Herdr tabs is not built yet; the user is still experimenting with it.
- **`implement` is forked to be model-invoked**, so an orchestrator's sub-agents can load it, and to commit only when the delegating agent doesn't. Upstream it is user-invoked and always commits.
- **The orchestrator commits each ticket.** Delegates share one checkout, so one commit per ticket keeps each ticket's changes apart.
- **Tool references hold the tool, skills hold the workflow.** `treehouse.md` and `herdr.md` carry each tool's everyday commands and gotchas; the order of steps (such as closing an effort after its merge) lives in the skill that runs it.
- **Tabs are labelled `<effort> · <role> · <harness>`**, appending to an existing label rather than replacing it, with the harness short (`CC` for Claude Code, `Codex`, `OpenCode`, `Cursor`), so the user can tell sessions and harnesses apart at a glance.
- **The orchestrator reads `lifecycle.md` every time it orchestrates**, not only when asked: without it the orchestrator lacks the context of where its part sits.
- **The final branch review and its fixes are delegated too**, like the tickets, so the orchestrator's context stays on coordination.
- **Prompts use each harness's skill syntax.** Claude Code starts a skill with `/name`, Codex with `$name`; the skills that write prompts for another agent say so in one line rather than keeping two copies of each prompt.
- **Decisions are recorded here, not as ADRs.** Most workflow decisions are easy to reverse, which fails the ADR bar, but the history still matters to whoever changes the workflow next.
- **A tab that has handed over is marked ` [settled]`**, appended to its label, instead of being relabelled `Thinking` at handover. The user asked for it: the marker says the session is finished and the tab is only a record, which a role name doesn't. The `Thinking` role label from `init-effort-with-herdr` still names the tab while the session is live.

## 2026-09-28

- **`to-spec` and `to-tickets` are forked to be model-invoked**, the same way `implement` was. Upstream they are user-invoked, so a thinking session started with a pasted or sent prompt couldn't load them, and wrote the spec by hand or asked the user to type the commands. The forks drop `disable-model-invocation`, set `allow_implicit_invocation: true` for Codex, and gain a "Use when" clause so the model knows when to load them. Everything else stays as upstream, so a diff against upstream shows only these changes. The upstream installs are removed once the forks are installed.
- **On a local-files tracker, an effort's spec and tickets live in `.efforts/<effort>/`** (`spec.md`, `issues/<NN>-<slug>.md`), tracked, per the folder standard; `.scratch/` is ignored and holds only temporary agent files. Upstream `to-tickets` wrote tickets to `.scratch/<feature-slug>/issues/`, which the folder standard makes ignored, so the forks write to `.efforts/` instead. Without an effort, `<effort>` is a short slug for the feature.
- **`to-tickets` names a ticket by its title, never by its number alone** (`#12 Add login`, not `#12`), in the breakdown, in "Blocked by", and when talking to the user. A bare number means nothing to a reader without the tracker open.
- **Handover is its own skill, and the mechanism is another.** `handover` owns the flow of starting a session outside this one: the readiness checklist, the starting prompt, picking a mechanism, and confirming the new session started, like `orchestrating` owns the discipline. `handover-to-herdr` is the Herdr mechanism. Together they replace `orchestrate-with-herdr`, whose name described the receiving side while the sending side ran it. This reverses the 2026-09-24 entries that put the handover in `orchestrate-with-herdr`.
- **A handover can happen at any point, from any session**, not only from a thinking session to an orchestrator: a desktop-app session can hand an effort to Herdr, and a thinking session can hand over to a fresh thinking session. Only the orchestrator has a receiving skill; any other session starts from a one-line "continue from the handoff" prompt.
- **`orchestrate-with-handoff` stays the receiver, tool-agnostic.** There is no Herdr-specific receiver: the handoff is the input on every path. It no longer assumes the handing session is reachable, because a desktop-app session isn't a Herdr tab; when the handoff says the session can't be reached, the orchestrator decides open questions itself and records them for the pull request.
- **`handoff` is forked from Matt Pocock's skill** as model-invocable, writing `.handoff/<date>-<topic>.md` in the repository and leaving it uncommitted for the session that hands over. This reverses the 2026-09-24 entry that stated the handoff's requirements inline instead of calling the upstream skill: upstream saves to a temp folder and is user-invoked, and the fork fixes both. *Handoff* is the document; *handover* is starting the other session.
- **`handover` and `handover-to-herdr` are model-invoked**, because the handing session runs them itself and `init-effort` points at them. `orchestrate-with-handoff` stays user-invoked: its one-line starting prompt arrives as a real slash command.
- **The starting prompt is always one line** (`/orchestrate-with-handoff <handoff>`, or "Continue from the handoff at <path>."), and everything else goes in the handoff. `herdr agent prompt` delivers text as a paste, and Claude Code collapses a paste of more than three lines or 800 characters into pasted content, which never runs as a command: a four-line handover prompt left the orchestrator asking for a go-ahead, while a one-line prompt sent the same way started the skill (see `docs/research/agent-skill-invocation.md`). This reverses the 2026-09-24 entry that put the worktree, branch and thinking session in the prompt.
- **Receiving the handover is the maintainer's go-ahead.** The receiving session starts work without asking for one and asks only for inputs only the maintainer has; the handing session collects those before it hands over.
- **`init-effort` hands over through `handover`** instead of printing its own prompt, so the prompt's shape lives in one place.
- **Herdr from anywhere.** `handover-to-herdr` checks the server with `herdr status`, not `HERDR_ENV`, so a desktop-app session can hand over to a Herdr tab. Its safety comes from targeting instead: explicit IDs from Herdr's JSON, `--no-focus`, never `--current`. The upstream `herdr` skill isn't forked; `handover-to-herdr` states the rule and carries the commands it needs. This reverses the 2026-09-24 entry that desktop apps can't drive Herdr.
- **From outside a pane, `worktree open` always gets `--workspace`**, the repository's own workspace (a plain workspace on the main checkout works). Without it the source workspace depends on state and the call can fail with `linked_worktree_source`.
- **A "trust this folder?" prompt goes to the maintainer.** A new worktree path shows it at agent start, which Herdr reports as `agent_not_ready`; it is a security decision, so the skill reads the screen and asks the maintainer to accept it in the tab.
- **The handover is fire-and-forget:** `agent wait --until working` confirms it, not `agent prompt --wait`, which waits for the agent to settle and times out on a long run. The handing session doesn't check on the new one afterwards.
- **The handing session stays on its own checkout.** It writes into the worktree by absolute path and commits with `git -C`, so a desktop session keeps its thread on the default branch. The worktree branches from the local default branch when the work builds on unpushed commits there. Pre-handover commits run one per call, because a rejected chain can stop halfway.

## 2026-09-28: the build loop

- **The orchestrator starts from a clean worktree.** Before the first delegate it commits any uncommitted changes in their own commit. A worktree can still reach the orchestrator dirty after the thinking session's clean ending, and protecting files "another session owns" cost a whole run (paths named one by one, no full format, every status view cluttered) and bought nothing.
- **"Done" is every acceptance criterion ticked on evidence.** The delegate's report gives evidence per criterion, and the orchestrator ticks only what it shows. A criterion shown only outside the checkout stays unticked with a note, so "done" never has to choose between ticking an unproven box and leaving a proven one blank. On a local tracker the ticks and status land in the ticket's own commit; on a hosted one the issue's checklist is ticked and the issue closed. An orchestrator had changed only a `Status:` line and read that as the skill's rule, because the skill never said what "done" meant.
- **Delegates stop what they start, and the orchestrator sweeps for leftovers.** `implement` stops its servers, tabs, background commands and watchers before reporting, and names anything left running on purpose; the orchestrator checks each report for leftovers and sweeps its own before saying a run is finished. A verification server ran for hours after its delegate finished, and a backgrounded formatter with an empty file list waited on stdin for an hour, so `implement` also carries the one-line zsh gotcha behind it.
- **Tickets run in parallel by default, each delegate in its own git worktree.** Only the step that uses a shared resource (an installed app, one real UI, a port, a database) is serialised; overlapping files are not a reason, since conflicts are cheap at integration. This reverses the 2026-09-24 entry "the orchestrator commits each ticket" as far as the shared checkout goes: a delegate now commits once in its worktree, and the orchestrator cherry-picks it with `--no-commit`, ticks its criteria, and commits it as the ticket's own commit, then tests, installs and checks the real app once per batch. A seven-ticket run took 74 minutes one after another because "only disjoint files" serialised tickets whose real constraint was one installed app. Machine-specific limits (a small VPS that builds serially) belong to the cloud-agents effort.
- **The orchestrator sets each ticket's review depth.** `implement` reviews at the depth its brief sets (none, one light pass, or `code-review`), and runs `code-review` only when nobody delegated it. Per-ticket two-reviewer passes took about a quarter of each ticket's time and duplicated the branch review at delivery; a large or risky ticket still gets its own.
- **A delegate brief points and names what comes back.** It carries paths, the review depth, the shared resources left to the orchestrator, and the report's shape (evidence per criterion, proof no temporary verification code is left, anything left running); it leaves out paraphrases, documented recipes and commit rules. Verification prefers the real app over off-screen renders: the renders cost time and missed a bug the first real-screen check found.

## 2026-09-28: the folder standard

- **One folder standard for agent records, defined once in `orchestrating/folders.md`.** `.handoff/<date>-<topic>.md` (tracked), `.efforts/<effort>/` for a local tracker's spec and tickets (tracked), `docs/agents/issue-tracker.md` for which tracker the repo uses, `docs/assets/<topic>/` for screenshots worth keeping, and one ignored `.scratch/` for agent notes, logs, temp files and the pull request description source, with `.claude/worktrees/` also ignored. Records had been scattered across `.scratch/`, `.handoff/` and `.humanlayer/`; each writer now points at the one file instead of restating paths. It lives beside `lifecycle.md` because the orchestrator reads that every run, and a reference file lets `to-pr` and `init-effort` point at it without loading the whole lifecycle.
- **`to-pr` drops the `.humanlayer/` prefix and saves its description source to `.scratch/pr-<number>/description.md`.** The prefix came with the fork of HumanLayer's `visual-pr`; upstream saved to HumanLayer's product task folder, synced to its cloud, not to git. Without that cloud nothing syncs, and GitHub already holds the description, so the source is temporary and belongs in the ignored folder. The licence file stays as the fork's credit. No `.prs/` folder and no `tmp/`: one ignored folder is enough.
- **The PR debrief is not a separate file.** The spec replaced it with `to-pr`'s last section (things to be aware of), so it lives in the description, in the pull request and in its `.scratch/` source.
- **Tracker-agnostic:** with a hosted tracker the spec and tickets live there and a project has no `.efforts/`; with a local one `.efforts/` holds them. This repo tracks on GitHub, so it gets `docs/agents/issue-tracker.md` and no `.efforts/`.
- **This repo migrates itself** (`.gitignore` gains `.scratch/` and `.claude/worktrees/`; `.handoff/` stays). Other projects migrate through tickets in their own trackers, following the migration table in `folders.md`. `to-spec` and `to-tickets` already write `.efforts/` and don't point at `folders.md`, to keep their diff against upstream to the intended change.

## 2026-09-28: talking to the maintainer

- **The orchestrator rarely asks.** The thinking session gathers every input only the maintainer has (credentials, IDs, accounts, external setup) before the handover, while they're present, and the handoff records them; a secret stays out of chat and committed files, and the handoff says where it lives. The orchestrator decides every other open question itself, keeps a list of those decisions with their reasons, and puts them in the pull request's last section. A request dropped into a progress update ("send the client ID any time") left the maintainer to decode what it was, why it was needed and where to answer; batching questions at stop points was considered and dropped, since a question the orchestrator can answer itself costs the maintainer more than a decision they review in the pull request.
- **It interrupts only for a critical blocker**, when nothing can continue: a notification plus one question in a fixed shape (the question first, the facts it rests on, a table of options with the pick marked, a one-line close). That shape is the one the maintainer called "a lot better" after asking for a prose question to be redrawn; **show-me** adds a picture where it helps weigh the options, rather than being the default for every question. This folds in "an orchestrator asks its questions with show-me".
- **Notifications at two moments only, done and blocked, from one reference.** `orchestrating/notify.md` holds when (the pull request delivered; nothing can continue without the maintainer) and what (one line under 200 characters, leading with what the maintainer acts on); every skill that notifies points at it. **How** is left to the maintainer's own agent instructions, else the harness's built-in tool: the built-in tool reported success under one terminal multiplexer while nothing arrived, and the working fix (a macOS command) is one machine's answer that will change, so the skills don't hard-code it.
- **Three common working-style points live in the skills that own them, not in a shared file.** How the maintainer likes to work depends on the project, so there is no working-style file; the three points common to every project each go where they're used. Decisions come with their facts, options and a pick (`orchestrating`; `grilling` is upstream and not forked, so it's left as is). Visual reports follow `show-me`, which the others point at rather than restate. Issues and pull requests are named by title, never by a number alone (`orchestrating`, `to-pr`, and `to-tickets` already). These points kept being rediscovered each session and copied into handoffs, where the next session might not read them.

## 2026-09-28: starting an effort or a project

- **`init-effort` is the one start; `init-effort-with-herdr` is retired.** The two differed only in the mechanism: the worktree tool and how the thinking session starts. `init-effort` now creates the worktree with the project's own tool (Treehouse by default when installed, else the environment's feature or `git worktree`) and suggests starting the thinking session in a Herdr tab through `handover-to-herdr`, with this session or a pasted prompt as fallbacks. This reverses the 2026-09-24 entry "Two paths: plain and Herdr" as far as the start goes.
- **`init-effort` also starts a brand-new project.** A new project differs from an effort only before the worktree exists: it gets a folder under the maintainer's projects folder (named in their instructions, never hard-coded), `git init`, a README, a licence, the folder standard's setup (`.gitignore`, `docs/agents/issue-tracker.md`), a first commit and `gh repo create`. The first commit and `origin` let Treehouse lease worktrees of it, so the project's first effort then runs the normal path. Public or private is asked every time, because publishing a repo can't be undone quietly. A session improvised all this once, with no commit, no remote and no worktree, and had to skip Treehouse.
- **The thinking session starts from a handoff and a one-line prompt naming only loadable skills.** `init-effort` writes the idea into `.handoff/<date>-<effort>.md` in the worktree, and the starting prompt names `grilling`, `prototype`, `to-spec`, `to-tickets` and `handover` in words rather than as slash commands, so it works the same in every harness and never names a user-only skill such as `grill-with-docs`. A pasted multi-line prompt, or one naming user-only skills, left an earlier thinking session writing the spec by hand.
- **`treehouse.md` moves beside `init-effort`; `herdr.md` goes.** `init-effort` is where a worktree is created, so the Treehouse reference lives there. `handover-to-herdr` already carries every Herdr command the start needs, so a second Herdr reference would duplicate it. The closing steps after a merge stay in `init-effort` until a closing skill takes them over.

## 2026-09-29: delivering

- **The pull request's last section, *Things to be aware of*, is the one report-back channel.** `to-pr`'s template ends with four short lines: decisions made alone, surprises, what's not in the PR, and follow-ups, each marked as a ticket, a todo for the maintainer, or nothing needed; an empty line says "None." so the reader knows it was considered. Any agent that opens a pull request fills it; `orchestrate-effort` fills it from the orchestrator's running list of decisions and what delegates reported. A delegated orchestrator had learned things during a build (a skipped end-to-end rerun, changes with wider reach than the ticket, review findings left unfixed) that reached neither the pull request nor a ticket, and surfaced only when asked for a debrief. A separate debrief file was considered and dropped: one pull request is the whole delivery, and a session closing the effort reads the section first. It stays apart from *Special things to note*, which is about the change itself.
- **`orchestrate-with-handoff` runs on the spec and tickets the handoff names**, not an effort folder, since a GitHub-tracked effort has none.
- **The worktree is clean after delivery, and the orchestrator reports it.** `orchestrate-effort` owns the rule, since it's the step that ends a build; it checks `git status` and reports a clean tree or names each file left out with its reason. Delivery writes nothing that needs committing: `to-pr` saves the description's source in the ignored `.scratch/`, and a rerun rewrites it there. An orchestrator had left `to-pr`'s saved description untracked in the worktree, because nothing said whether to commit it; the folder standard answered that by making the folder ignored.
- **After delivery the maintainer only reviews and says "go"; the rest is the agent's.** The final report lists what the agent will do once told, as its own steps: merge, run the post-merge follow-ups, try what can only be tried after the merge, and close the effort with `close-effort`. A delivery report had ended with a "next steps for you" list of which only the first line was the maintainer's.
- **QA by the maintainer is opt-in per project and non-blocking by default.** A project opts in through its own instructions, which also say how a build reaches the maintainer (an install, a dev server, a preview link); a CLI or a skill usually needs none. A ticket the maintainer can use stays open after it's built, assigned to them, with a "Ready for you to try" comment (how to reach the build, how to use it, numbered try-this steps, what to do when done), and the pull request says "Refs", not "Closes", because "Closes" had auto-closed tickets at merge before anyone tried them. The merge waits only when the spec says "QA: blocking", decided in the thinking session for UX-heavy work the maintainer will iterate on. It lives in `orchestrate-effort`'s build step, with the "Refs" rule in `to-pr` and a line in `lifecycle.md`'s Build phase, rather than a new skill: it's one step of the build, and `to-spec` (a fork) stays unchanged, since the spec only needs to say "QA: blocking" in its own words. Closing the built ticket and opening a separate QA ticket was considered and dropped: keeping the one ticket open and assigned to the maintainer puts it in their issues list with its history.

## 2026-09-29: closing

- **`close-effort` is its own skill, model-invoked.** It runs when the maintainer tells the orchestrator the pull request is good ("go"), or when any session is told the pull request merged or to merge it; a skill the agent must reach from those words needs a description, so it is model-invoked with `allow_implicit_invocation: true` for Codex. Every close so far needed the maintainer to ask for each part by hand: checking the merge, auditing what was left, carrying it over, closing tickets, removing worktrees and branches, closing the Herdr workspace. The closing steps `init-effort` carried from the retired `init-effort-with-herdr` move into it, and `init-effort` and `lifecycle.md`'s Close phase point at it. This completes the 2026-09-28 entry that kept those steps in `init-effort` until a closing skill took them over.
- **The agent merges, and runs every cleanup command itself.** The maintainer's only step after delivery is review and "go"; a close that ended by handing the maintainer the commands to paste was the example of what not to do.
- **It reads *Things to be aware of* before anything else,** and routes each item to a check run now, a next-effort ticket, a todo for the maintainer, or nothing needed. The section replaced the separate debrief, and a close that read a debrief first caught a skipped end-to-end rerun nobody else knew about. Without the section (an older effort), it asks the delivering orchestrator once through Herdr when that session is still alive, else reads the handoff and tickets.
- **Unfinished work always ends as linked next-effort tickets,** labelled for the next effort, never dropped. QA tickets left open for the maintainer (non-blocking QA, "Refs" in the pull request) aren't unfinished work: they stay open and assigned, with a comment that the work is merged.
- **Destructive steps need proof, and a denial is final.** A branch or worktree goes only when its work is proven merged: reachable from the default branch, or matched by patch with `git cherry`, because sub-agent work is often cherry-picked with fixes or squashed and reachability alone misses it; anything unproven is kept and reported. When a permission check refuses a deletion, the command goes into a script in the main checkout's `.scratch/`, each line under its proof, for the maintainer to run, and the agent tries no variant: an earlier close had `git worktree remove --force` and `git branch -D` refused as irreversible local destruction. (The claim that `git cherry` catches squashed or fixed-up work is wrong; see *Proving merged work* below.)
- **Ignored and untracked files are copied out first.** `treehouse return` and `git worktree remove` delete them without warning (an untracked `.vscode/` would have been lost), so the skill lists them per worktree and copies what's worth keeping per the folder standard.
- **Its own worktree goes last, from a Herdr tab outside it.** Returning a worktree stops every process in it, the closing session included, so after its report the skill opens a tab in the repository's main-checkout workspace and runs the return (after a short pause) and the workspace close there; the tab's output is its report. Without Herdr, that one step is the maintainer's. Worktrees are returned to the Treehouse pool rather than destroyed, so the pool keeps its warm slots.

## 2026-09-29: branch review

- **Proving merged work.** Corrects the proof in *Destructive steps need proof* above: `git cherry` matches commits by patch, so it prints `+` both for an effort branch that was squash-merged and for a delegate commit integrated with `cherry-pick --no-commit` plus ticked criteria (checked in a throwaway repo). `close-effort` adds a third proof: the pull request is `MERGED` and the branch's tip is its `headRefOid` or an ancestor of it; a leftover delegate branch counts when its ticket's commit is in that head and it holds nothing else. `orchestrate-effort` now removes each delegate's worktree and branch right after its ticket commit is integrated and pushed, the integrated commit being the proof, so few delegate branches reach the close.
- **The close leaves the maintainer's main checkout where it is.** It runs git there with `git -C`, pulls only when the checkout is clean and already on the default branch, and otherwise fetches and works from `origin/<default>`; switching branches under the maintainer could strand their work in progress.
- **The close commits nothing straight to the default branch.** Its own changes to tracked files (a local tracker's done marks, files kept from worktrees) follow the project's instructions, and by default go on a small follow-up branch with a pull request through `to-pr`, or are listed in the report when too small for one. It matches how every other change reaches the default branch.
- **The install names the upstream skills one by one.** Installing all of `mattpocock/skills` beside the family would put the upstream `handoff`, `to-spec` and `to-tickets` over the forks, so the README and `lifecycle.md` list only the upstream skills the family cites (`grilling`, `prototype`, `tdd`, `code-review`, `setup-matt-pocock-skills`) and say the forks replace the other three.
- **The handover settles QA before it hands over.** In a project that opts in to QA, `handover`'s readiness check asks that the spec say whether QA is blocking, and asks the maintainer while they are present when it doesn't; otherwise nothing prompted that choice and every effort fell to the non-blocking default unasked.
